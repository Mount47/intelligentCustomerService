## 什么是 bad case（项目级统一口径）

**Bad case = 在明确前置条件下可复现，并使系统实际行为偏离业务预期、安全约束或工程目标的案例。** 它不只指“意图识别错了”，还包括：

- **理解错误**：意图、极性、指代、多意图、槽位识别错误；
- **流程错误**：状态续接失败、非法转移、确认门被绕过、错误转人工或错误自助完成；
- **数据与安全错误**：越权读取/绑定、硬事实幻觉、跨用户串数据、敏感信息泄漏；
- **写入正确性错误**：重复退款、幂等失效、并发覆盖、重试产生副作用；
- **可用性错误**：超时、上下文溢出、熔断/限流异常、worker 重试或队列行为错误；
- **产品/API 错误**：前后端契约不一致、入口参数未校验、错误码不正确、交互无法闭环；
- **评测错误**：标签错误、夹具不合法、指标掩盖失败、文档数字与实跑不一致；
- **可观测性错误**：实际失败但 trace 显示成功，或成功结果被 FAILED 噪声污染。

### 每条 bad case 必须记录什么

1. **模块与严重度**；2. **前置条件/输入**；3. **期望行为 vs 实际行为**；
4. **根因**；5. **修复方案**；6. **回归测试或复现命令**；7. **commit**；8. **剩余边界**。

纪律：发现后先记本文件；未修的同步进
[待办事项](../architecture/待办事项.md)；形成稳定架构选择再进
[当前架构决策](../architecture/架构决策.md)。修复不能只改代码，必须尽量补最小回归测试。

## 1. 前端 dev 模式永远走 mock，连不上后端 ✅
- **现象**：`npm run dev` 下，即便设 `VITE_USE_MOCK=false`，前端仍显示 mock 假数据，从不请求后端。
- **根因**：`frontend/src/api/client.ts` 旧逻辑 `USE_MOCK = VITE_USE_MOCK==="true" || import.meta.env.DEV`。dev 模式 `DEV===true` 恒为真 → 永远 mock，`=false` 无效。
- **解决**：改为"显式设置优先"——`=true` 强制 mock、`=false` 强制连真后端（即便 dev）、未设时 dev 默认 mock。
- **关联**：commit `f97d543`；`frontend/src/api/client.ts`、`frontend/.env.local`。

## 2. vite proxy 剥离 `/api` 前缀导致 404 ✅(绕过)
- **现象**：走 vite proxy 时请求打到后端 404。
- **根因**：`vite.config.ts` proxy `rewrite: path.replace(/^\/api/,"")` 把 `/api` 删了，但后端路由带 `/api` 前缀。
- **解决**：`.env.local` 用绝对 URL `VITE_API_BASE_URL=http://localhost:8000/api` 直连后端，绕过 proxy（后端已开 CORS，实测 `Access-Control-Allow-Origin: *`）。
- **遗留**：proxy 本身仍是错配的；若以后想用 proxy，需去掉该 rewrite。

## 3. `.venv` 未装 uvicorn，后端起不来 ✅
- **现象**：`python -m uvicorn ...` 报 `No module named uvicorn`。
- **根因**：`uvicorn` 在 `pyproject` 声明了，但 `.venv` 漏装。
- **解决**：`.venv/bin/python -m pip install "uvicorn[standard]>=0.32"`。

## 4. 评测集 oos-1 标注错误 ✅
- **现象**：`run_eval --real` 唯一 FAIL：oos-1（"今天天气怎么样"）期望 `general_policy_query`，qwen 判 `out_of_scope`。
- **根因**：测试集标注错了——"今天天气"本就是超范围，模型判得对；且规则分类器无超范围关键词，只能兜底 `general_policy_query`，stub 与 real 天然不同。
- **解决**：引入 `accept_intents`（一组可接受意图），oos-1 接受 `out_of_scope` / `general_policy_query` 二者（都路由 general、都 resolved）。坐实"评测能反查出测试集自身 bug"。
- **关联**：commit `f6aab2a`；`app/eval/test_cases.json`、`app/eval/run_eval.py`。

## 5. 工具调用 FAILED：LLM 拿不到 order_id 瞎猜参数 ✅
- **现象**：真实模型下，思考过程里 `get_order_detail` 等工具标红 FAILED；每次思考路径不一致；但最终退款结果仍正确。
- **根因**：`get_order_detail` 要 `order_id`(整数)，但 loop 只把"系统提示 + 用户原话"给 LLM，**没注入后端已解析出的 order_id/user_id**。LLM 只能瞎猜（传 order_no 字符串 / 猜数字）→ 工具失败、且每次猜法不同。结果仍对，是因为 `finalize` 用的是 `ctx.order_id` 真值（读写分离兜底掩盖了这个 bug）。
- **影响**：① LLM 解释无数据接地；② trace 被 FAILED 污染，误导排障；③ 思考过程不稳定。
- **已解决（两层叠加）**：
  - **软层·prompt 注入**：`agent_core._context_note(ctx)` 把 `user_id`/`order_id` 拼进 system 提示，`_run_loop` 调 LLM 前注入 → 让 LLM 推理/解释引用得对（软约束，提升体验，不保证）。
  - **硬层·参数绑定**：`_exec_tool` 在 `execute` 前调 `_bind_context_args`——按工具 schema 用会话真值**覆盖** LLM 所填的 `user_id`/`order_id`（`ToolRegistry.schema_props` 提供参数名）。LLM 填错/越权传他人 id 都无效 = **确定性保证 + 越权(IDOR)防护**。
  - **为什么两层**：prompt 让模型"说得对"，绑定让工具"做得对、不越权"；任何喂给模型读的东西都是概率性遵循，硬保证只能来自"不让模型决定关键值"（同 finalize/读写分离哲学）。
  - **不改变业务结果**：退款决策仍由 finalize 用 ctx 真值确定性执行。
  - **验证**：`test_context_note_includes_known_ids`、`test_context_injected_into_system_prompt`、`test_context_binding_overrides_llm_args`(LLM 传越权 id 被覆盖为会话真值)；全套 79 passed。（真实 qwen 的 FAILED→PASS 对比待按需录。）
- **关联**：commit 见下；`app/agent/agent_core.py`、`app/tools/base.py`、`app/tools/order_tools.py`。

## 6. 超范围问题只有软护栏，泛泛挡话 ✅
- **现象**：问"今天天气""我想买衬衫"，每轮都回泛泛的"我是售后助手…"挡话，行为不稳定（靠模型自觉）。
- **根因**：out_of_scope → 兜底 GeneralSkill，回复 = LLM 自由生成；系统提示是软约束，无确定性拒答；postcheck 只拦禁语，**不管跑题**。
- **已解决（P0 scope 硬闸）**：明确超范围线索(`_OUT_OF_SCOPE_CUES`：天气/写诗/闲聊…)→ classify 判 `OUT_OF_SCOPE`；`handle` 路由前 scope 闸 → **固定拒答短路，不跑业务 LLM/不调工具**。连"今天天气"都变成硬约束。
  - **诚实边界**：规则层只能挡"确信的超范围"；模糊的落低置信澄清；鲁棒的 scope 识别仍待语义层(LLM defer)。
- **关联**：commit；`app/agent/intent_classifier.py`、`app/agent/agent_core.py`。

> 一并落地的 P0 同伴：② 确认态专用 `parse_confirmation`(强确认/强取消/迟疑 fail-safe，根治"不确定"类)；③ 低置信 `Confidence.LOW`→统一澄清，不进技能。三者合成 handle 路由前的 guard 链。

## 7. 无对话记忆（跨轮不记得）✅(P1)
- **现象**：第一句说"我买了件衣服"，下一句问"我买了什么"，Agent 不知道。
- **根因（三层）**：① 前端每条消息不带 ticket_id → 每条新建工单，对话不成线程；② `runner` 只取最新一条消息、`ctx.history` 从不加载历史 → LLM 无状态；③ "买了啥"的权威来源本应是 orders 表，不是聊天记忆。
- **解决（P1 短期对话记忆）**：`runner._load_history` 加载本工单历史(窗口 20)进 `ctx.history`；前端 `SendMessageRequest.ticketId` + ChatView 串 ticketId/「新对话」按钮。
- **边界**：仅**同一对话内**短期记忆，且需 qwen(stub 忽略历史)；跨会话长期记忆=P3/P4；事实接地("真实买了啥"查 orders)=P2，均待做。
- **关联**：commit `f5a1fd9`；`app/workers/runner.py`、`frontend`、`tests/test_memory.py`。

## 8. 退款追问被 finalize 劫持 + 会话级重复建草稿 ✅
- **现象**：同一工单连发"我要退款 订单X"→"我刚才问的订单号是多少"→"我刚才说了什么"，**每轮都回"已为您创建退款申请…"**，追问从不被回答；疑似每轮新建一条退款草稿。
- **根因**：① 每轮**独立重新分类**意图，追问也被判 refund_request；② 工单上已沿用 order_id；③ 命中 RefundHandlingSkill → `finalize` **确定性执行**退款，只认"退款意图+订单"，不读这句到底问什么 → 回固定话术，LLM 对话输出被丢弃（所以 P1 记忆在退款回合里看不出效果）；④ `create_refund_draft` 的 `business_key=sha(user|order|refund|消息文本)`，每轮文本不同 → 不去重 → **重复建草稿**（三层幂等防"同请求重发"，防不住"同订单不同对话轮次反复触发"=会话级重复）。
- **本质**：读写分离/finalize 确定性带来安全，代价是"业务技能里不能对话"。
- **坐实**：实测 DEMO-REFUND-LOW 一个订单建了 **7 条**草稿，含 reason="我不要退款""我刚才退款的订单号是多少"（否定/追问都触发了建草稿）。
- **已解决（会话级幂等）**：`refund_service.get_active_refund` 查该用户该订单是否已有进行中退款(draft/pending_human/approved)；`RefundHandlingSkill.finalize` 取订单号后、查政策前先判：已有则不再新建，回"您该订单的退款(单号#X)已在处理中/审核中"。三层幂等防"同请求重发"，这层防"同订单跨轮反复触发"。
  - **验证**：单测 `test_refund_no_duplicate_draft_same_order` / `test_refund_inflight_pending_human_not_duplicated`；e2e 连发 5 条(含追问/否定/换措辞)→ 仅建 1 条(修复前 7)。全套 76 passed。
- **遗留更新**：
  - ① 否定/疑问**误判已修**（结构化意图）："我不想退款了"→`cancel_refund`、"能退款吗"→`refund_inquiry`，**不再误建草稿**。**取消退款动作也已落地**（步骤2：撤待确认 / 撤已建草稿）。
  - ② 追问("我刚才说了啥")仍未给真正的会话型回答(需追问路由 + P1 记忆作答)。

### 关联升级：结构化意图识别（关键词召回 → 极性 → IntentResult）

- **关键词只做候选召回**，退款族再按极性定 intent：否定→`cancel_refund`、疑问→`refund_inquiry`、肯定→`refund_request`(requires_confirmation=True)。

## 9. “不确定”被误判为确认，可能触发退款 ✅

- **模块/严重度**：确认协议 / 严重。
- **Bad case**：工单处于 `waiting_user_confirm`，用户回复“我不确定”“不可以”“再想想”；旧通用子串逻辑因包含“确定/可以”而可能当成确认。
- **期望 vs 实际**：期望保持等待且不写；旧行为可能进入退款执行。
- **根因**：高风险确认复用了通用意图/子串判断，没有否定与迟疑优先级。
- **修复**：确认态走独立 `parse_confirmation`，按 `CANCEL → HESITATE → CONFIRM` 判断，默认 `UNCLEAR`；只有强确认才能执行，并绑定 `pending_action`。
- **回归**：`tests/test_intent.py::test_uncertain_not_confirmation`、`tests/test_skills.py::test_uncertain_in_confirm_does_not_execute`。
- **剩余边界**：纯词表会漏掉“妥了/OK”等表达，但漏判只多问一轮，失败方向偏安全。

## 10. 关键词第一个命中直接胜出，多意图和否定表达误路由 ✅(P0)

- **模块/严重度**：意图理解 / 高。
- **Bad cases**：
  - “别转人工，我只想查物流”曾因“人工”优先命中而转人工；
  - “退款什么时候到账”曾因疑问词不全而进入退款请求；
  - “物流一直没收到，我还想退款”同时含物流异常和退款，旧逻辑由关键词表顺序静默决定。
- **根因**：规则层只返回第一个候选；极性主要覆盖退款族；规则命中后不再允许语义层消歧。
- **修复**：`RuleIntentClassifier.recall` 返回候选集合；过滤明确否定候选；处理退款广召回/订单对象等已知重叠；多候选限定集合 defer LLM，无 LLM/非法输出则 `LOW` 澄清；投诉升级信号确定性优先。
- **回归**：`test_refund_question_words_are_inquiry`、`test_negated_handoff_does_not_beat_real_intent`、`test_multiple_rule_candidates_require_disambiguation_without_llm`、`test_llm_disambiguates_only_among_recalled_candidates`。
- **关联**：commit `1eeaec6`。
- **剩余边界**：仍是单主意图输出；条件意图、多任务和置信度校准未完成。

## 11. LLM 意图输出按子串解析，解释文本可能选错标签 ✅

- **模块/严重度**：LLM defer 解析 / 高。
- **Bad case**：模型返回 `not refund_request, choose refund_inquiry`，旧代码遍历 Enum 做 `if intent in text`，会先选中 `refund_request`。
- **根因**：prompt 要求“只输出标签”只是软约束，解析器又容忍任意解释文本。
- **修复**：只接受精确枚举或严格 `{"intent":"..."}`；多候选消歧结果还必须属于召回集合；解释文本、多标签、非法 JSON 全部拒绝并降级。
- **回归**：`tests/test_intent.py::test_llm_explanatory_or_multi_label_output_is_rejected`。
- **关联**：commit `1eeaec6`。
- **剩余边界**：当前是 prompt + 本地严格校验，尚未统一使用 provider 原生 JSON Schema。

## 12. Chat 入口可绑定他人 order_id / 向他人 ticket 追加消息 ✅

- **模块/严重度**：API 接入与 IDOR / 严重。
- **Bad case**：请求体携带当前用户不拥有的 `order_id`，或携带他人的 `ticket_id`。旧 `accept_message` 会直接绑定订单，且取 ticket 后未校验 `ticket.user_id`。
- **期望 vs 实际**：期望在 Agent/工具调用之前拒绝；旧代码依赖下游部分 Skill 再校验，且 ticket 消息入口存在越权窗口。
- **根因**：把请求体里的资源 ID 当成可信上下文，归属校验放得过晚且覆盖不完整。

- **回归**：`test_accept_message_rejects_other_users_order`、`test_accept_message_rejects_other_users_ticket`；评测 `adv-bypass-owner` / `adv-cross-owner-query` 改为期望 `access_denied`。

## 15. 滚动摘要可能摘丢重要软约束 🔵/🟡

- **模块/严重度**：长对话记忆 / 中。
- **风险 case**：订单号和金额可重新查 DB，但“只退第二件”“不要原路退”“客服已承诺回电”“已经尝试重发”等软约束可能被摘要省略。
- **边界**：这不是向量记忆能自动解决的问题；向量召回同样可能漏召回或召回错误片段。
- **方案**：硬事实查 DB；流程关键字段结构化持久化；最近消息保留原文；滚动摘要只承担可容错的叙事上下文。摘要失败回退模板且不阻断主流程。
- **验收待补**：构造超预算长对话，验证 pending action/slots 不依赖摘要，关键流程不因摘要丢词而改变。

## 16. 多 worker stale write 覆盖工单状态，异常路径可能提交半成品副作用 ✅

- **模块/严重度**：状态机持久化 + worker 事务 / 严重。
- **Bad case**：两个 Session 同时读到 `created@v0`，先后处理同一 Ticket。旧 runner 最后直接 `ticket.status = ctx.state`，后提交者会覆盖先提交者；更严重的是，Skill/工具写已 flush 后若发生冲突，旧异常路径未先 rollback，`finally commit` 可能把退款草稿、Agent 回复等半成品一起提交。
- **根因**：状态机只校验单进程内的路径合法性，没有数据库层 compare-and-set；Ticket 没有版本号；runner 把“业务执行 + 状态落库”当普通赋值，异常路径缺少事务回滚。
- **修复**：
  - Ticket 新增 `version`；状态持久化统一为 `WHERE id=? AND status=? AND version=?` 的 DB 条件更新，成功后 `version+1`。
  - `rowcount=0` 抛 `ConcurrentStateUpdate(409)`，stale writer 不得覆盖赢家。
  - runner 在任何异常/CAS 冲突时先 `rollback()`，再单独落 session 的 failed/timeout/retry 信息；Agent 回复、Skill 写、工具写与状态 CAS 同事务成败。
  - `INFO_REQUIRED` 下的首次订单绑定也用 version CAS；并发绑定不同订单只允许一个胜出，同订单重复绑定幂等成功。
  - MVP 旧库兼容迁移补 `tickets.version DEFAULT 0`；正式生产仍应上 Alembic。
- **回归**：`test_ticket_state_cas_rejects_stale_writer`、`test_ticket_order_binding_cas_rejects_different_concurrent_order`、`test_runner_cas_conflict_rolls_back_all_side_effects`；后者同时断言临时业务 Ticket 和 Agent 回复均未落库。全量 **156 passed**（2026-07-15）。
- **关联**：commit `8b7cf15`。
- **剩余边界**：测试已制造确定性的 stale-session 交错并验证 DB CAS；退款 64 线程有 PG 证据，但状态 CAS 尚未单独跑 PG 多线程压测，不能把本测试表述成吞吐数据。

## 17. 熔断 HALF_OPEN 惊群 + 迟到结果污染新状态 ✅

- **模块/严重度**：Provider 可用性 / 高。
- **Bad case**：熔断器 OPEN 冷却结束时，32 个并发请求几乎同时到达。旧实现先把状态切到 `half_open`，而 `allow()` 对 `half_open` 全部返回 `True`，导致所有请求一起打向尚未确认恢复的 provider。另一个时序问题是：旧 CLOSED 周期已放行的慢请求，可能在熔断器进入 OPEN 或新 HALF_OPEN 周期后才成功返回，并把新状态错误关闭。
- **期望 vs 实际**：期望 HALF_OPEN 只放一个探针，其余请求快速失败或走 fallback；旧行为会形成恢复瞬间的并发惊群，且请求结果没有所属状态周期，迟到结果可能污染当前状态。
- **根因**：状态检查、OPEN→HALF_OPEN 转移和探针占用不是同一原子操作；布尔型 `allow()` 不携带请求所属的 breaker epoch，`record_success/failure` 无法识别过期结果。
- **修复**：用进程内 `Lock` 串行化状态转移；生产包装器改用 `acquire()` 返回 `CircuitPermit(generation, probe)`，在同一临界区完成 OPEN→HALF_OPEN 并只发一个探针；HALF_OPEN 的其他请求直接降级/失败。只有 generation 匹配的当前探针能关闭或重新打开熔断器，旧周期迟到结果被忽略。
- **回归**：`test_half_open_allows_exactly_one_probe_under_concurrency` 用 32 线程断言仅一个探针；另有迟到 CLOSED 成功不能关闭 OPEN、不能冒充当前 HALF_OPEN 探针的回归测试。全量 **159 passed**（2026-07-15）。
- **关联**：commit `14e44e2`；`app/llm/circuit_breaker.py`、`tests/test_circuit_breaker.py`。
- **剩余边界**：熔断器仍是**进程内**状态；多 worker 进程各自最多放一个探针，集群级仍可能形成“每进程一个探针”。只有规模和故障演练证明有必要时，才考虑 Redis/集中式熔断协调。当前也没有把并发正确性测试包装成 QPS/P99 证据。

## 18. 上下文超限被当 provider 故障，原输入盲重试并污染熔断 ✅

- **模块/严重度**：LLM 适配层 / 可用性 / 高。
- **Bad case**：provider 返回上下文窗口超限。旧 adapter 不分类异常，熔断包装器把所有异常都计作 provider 失败；runner 标记 session failed，Celery 又对完全相同的输入最多重试两次。若超限恰好发生在 HALF_OPEN 唯一探针，还可能占住探针槽或误判 provider 恢复情况。
- **期望 vs 实际**：期望先缩短输入再有限重试；仍超限则确定性转人工，且不能继续 Skill `finalize` 或把客户端坏输入算成 provider 故障。旧行为是“原样重试必然再失败”，还可能错误打开熔断器。
- **根因**：缺少 provider 无关的异常分类；上下文预算只有调用前预防，没有 provider 真报超限后的 backstop；熔断、Celery 重试和业务流程都只能看到普通异常。
- **修复**：
  - Claude/OpenAI-compatible adapter 将稳定错误 code/消息归一化为 `ContextWindowExceeded`；未知异常保留原类型。
  - 最外层 `ContextBackstopLLMClient` 仅在输入**确实能缩短**时，丢弃当前用户轮次之前的软历史并严格按字符预算压缩当前轮工具链，最多重试一次；短输入不做假重试。
  - `CircuitBreakerLLMClient` 不把该异常计入 provider failures；HALF_OPEN 探针遇到坏输入会释放并立即允许后续合法请求重新探测，不会卡死探针槽。
  - 二次超限由 `AgentCore` 固定话术转 `NEED_HUMAN`，清理 pending context，不执行工具或确定性写入；异常被业务闭环，因此 Celery 不再原样重试。
- **回归**：覆盖两类 adapter 归一化、有效压缩一次成功、二次超限不三试、短输入不假重试、工具调用后缀保留、超限不触发熔断、HALF_OPEN 槽位不锁死、二次超限转人工且无工具副作用。全量 **168 passed**（2026-07-15）。
- **关联**：commit `8003e35`；`app/llm/errors.py`、`app/llm/context_backstop.py`、`app/agent/agent_core.py`。
- **剩余边界**：错误识别依赖 provider 稳定 code 和保守消息片段，新 provider 的新错误格式需补映射；紧急压缩会牺牲软历史，因此只作最后 backstop，硬事实和流程键仍必须查 DB/结构化持久化。若 system prompt、工具 schema 或单条不可裁剪载荷本身过大，系统会直接转人工而不是反复重试。

## 19. 退款 service 提前 commit，Ticket CAS 冲突仍可能留下退款单 ✅

- **Bad case**：runner 先读取 Ticket `created@v0`，另一个 worker 将其推进到 `need_human@v1`；当前 worker 随后执行高风险退款并创建退款草稿，最后 Ticket CAS 失败。旧 `create_refund_draft()` 内部已经 `commit()`，所以 runner 的异常回滚只能撤销回复/附加工单，退款单可能永久残留。
- **根因**：service 把“独立调用时方便提交”和“作为 Agent 主事务的一部分”混成同一个事务契约；CAS 被设计成最终提交闸门，但下层 service 提前越过了它。
- **修复**：
  - `create_refund_draft(..., commit=False)` 与 `cancel_active_refund(..., commit=False)` 供 Refund Skill 使用，Agent 主链路不再由 service 提交。
  - PostgreSQL 唯一冲突用 savepoint 回滚本次 INSERT 并回查赢家；SQLite 外层事务规避最外层 savepoint 被驱动提前提交的问题。
  - service 独立调用默认仍 `commit=True`，避免无关调用方大面积改造。
- **回归**：`test_runner_cas_conflict_rolls_back_refund_write` 用真实 Refund Skill 制造 stale Ticket，断言 Session failed，同时退款、附加 refund Ticket、Agent 回复均为 0；补完本轮 P0/P1 后全量 183 passed。
- **后续闭环**：消息接入“先查后插”已用 savepoint + `IntegrityError` 回查赢家关闭并发窗口，PostgreSQL 16 线程通过。剩余边界是状态 CAS 的专项测试仍为确定性交错，不是 PostgreSQL 多 worker 吞吐证据。

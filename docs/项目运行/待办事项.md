## TODO-1 · 转人工时为人工客服生成会话摘要（handoff summary）

**状态**：💡 构想，未实现
**价值**：Agent 转人工时（state → `need_human`），人工客服不必从头读长对话，一眼看懂"用户要什么、已经做了什么、为什么转来、该接着干嘛"。

### 触发时机
- 仅在**转人工那一刻**生成（state 进入 `NEED_HUMAN`），不是每轮都做 → 成本低。
- 可同步生成，也可异步（不阻塞转人工动作；失败不影响转人工）。

### 分档策略（用户要点：太短不总结、太长保准确）
| 对话长度 | 策略 |
|---|---|
| **太短**（如 ≤ 3~4 条消息 / 低于 token 阈值） | **不总结**，直接把原始记录给人工（总结 2 句话没意义，还可能失真） |
| **中等** | 单次 LLM 总结 |
| **太长**（超 token 预算） | **map-reduce / 分段摘要**：先分段总结再合并，避免超上下文、避免丢信息 |

阈值配置化（放 config，如 `handoff_summary_min_msgs` / `_max_tokens`）。

### 摘要结构（结构化字段，不是一段自由散文 → 更准、人工更快看）
- **用户核心诉求**：用户到底要什么（保留其最后一次明确请求，长对话里尤其别丢）
- **涉及订单/实体**：order_no、金额、退款单号等
- **Agent 已采取的动作**：建了退款草稿 #X / 升级工单 / 查了什么
- **转人工原因**：高风险退款 / 投诉 / 非本人 / 工具失败 / 用户要求
- **待人工处理**：接下来人工要做的事
- **风险/敏感点**：情绪激烈、高金额、超期等

### 准确性保证（用户要点：数据要准）—— 复用读写分离哲学
**关键设计：客观事实从 DB/结构化记录取，不让 LLM 从聊天里"总结出数字"（防幻觉）。**
- **事实字段**（order_no、金额、退款单号#X、工单状态、转人工原因）→ 由**确定性代码**从 `tickets` / `refund_requests` / `agent_sessions` / `agent_tool_calls` 读出来填。
- **叙述字段**（用户诉求、对话经过）→ 由 **LLM 总结**对话文本，并在 prompt 里强约束"只依据记录、不得编造数字/订单号"。
- 即"**LLM 写叙述 + 代码填事实**"的混合摘要 → 数字一定对，诉求由 LLM 抓。
- 可选校验：摘要里出现的 order_no/金额与 DB 比对，不一致则以 DB 为准/告警。

### 实现草图（待实现）
- `services/handoff_service.summarize_for_human(db, ticket_id) -> HandoffSummary`
  - 取该工单全部 `ticket_messages`；按长度分档（短→跳过；长→分段）。
  - 事实字段：查 refund_requests / ticket / sessions 填充。
  - 叙述字段：LLM 总结（stub 下给确定性模板，保证 CI 可复现）。
- 落地：`tickets` 加 `handoff_summary`(JSON/Text) 字段，或作为一条 `system` 消息入 thread。
- 展示：`/api/admin/tickets/{id}` 详情里带上摘要，运维端人工接管时显示。

### 边界 / 风险
- **摘要失败必须降级**：异常时回退到"显示原始记录"，绝不阻断转人工。
- **PII**：摘要里避免堆砌敏感信息（手机号/地址按需脱敏）。
- **stub/CI**：stub provider 下走确定性模板摘要，不调真实 LLM。
- **成本**：仅转人工时触发，量小；长对话 map-reduce 注意 token 上限。

### 依赖 / 复用
- 已有：`tickets`/`ticket_messages`/`refund_requests`/`agent_sessions`/`agent_tool_calls`、LLM client、P1 历史加载、admin ticket 详情接口。
- 关联状态机：`need_human` 升级路径（refund 高风险 / 投诉 / 转人工）。

### 验收标准
- 短对话不生成摘要、直接给原文；中/长对话生成结构化摘要。
- 摘要里的 order_no/金额/退款单号与 DB **完全一致**（事实字段不来自 LLM 臆测）。
- 用户最后一次明确诉求在摘要中可见。
- LLM 失败时回退原文、转人工不受影响。
- stub 下确定性可复现，纳入测试。

## TODO-2 · 上下文溢出（context overflow）处理

**状态**：💡 待认真做（当前非紧急；客服消息短 + 已有 20 条历史窗口 + loop 迭代少 + 知识库小 → 现风险低）

**风险点（会溢出的地方）**：
- 超长多轮对话：`_load_history` 把历史灌进 loop（现窗口按"条数"`_HISTORY_MAX_MSGS=20`，不是按 token，仍可能超）。
- RAG 扩展后：检索多篇/长文档塞进 prompt。
- 大工具输出回灌。

**当前缺口**：
- 历史窗口**按条数不按 token**，不精确。
- 真溢出会**硬失败**：runner 捕获异常→标 `failed`/重试，而非优雅降级。
- 已在追踪 token（`token_acct` / `agent_sessions.history_tokens`），但没用它做**预算控制**。

**方案（便宜 → 正确）**：
1. 🟢 便宜：① `_load_history` 改**按 token 预算**截断（用 `history_tokens`）；② adapter/runner 捕获"上下文超限"错误 → **截断重试一次，仍不行→转人工**（"对话过长，已为您转人工"），把硬崩变软降级。
2. 🟡 正确（对话真变长 / 上 RAG 时）：**滚动摘要**——旧历史超预算就摘成一段再进 prompt。**与记忆分层 P4 + TODO-1 转人工摘要同一套机制，合并做，别单造**。

**验收标准**：
- 历史超 token 预算时自动截断/摘要，不超模型上下文。
- 构造超长对话时不再 `failed` 崩溃，而是降级（截断重试或转人工）。
- token 预算可配置；stub 下可复现、纳入测试。

**关联**：`app/workers/runner.py`(`_load_history`)、`app/llm/*`(adapter 错误处理)、记忆分层 P4、[[TODO-1]]。

## 优先级一：共享熔断状态

原优先级三。当前熔断器在单个工作进程内有效。多个工作进程之间不共享状态，
模型服务故障时仍可能分别探测。

可根据真实部署规模选择：

- 保留进程内熔断，并由统一模型网关限流；
- 使用 Redis 协调共享状态和探测许可；
- 交给服务网格或模型网关负责。

附带一处已知行为（2026-08-03 验收时暴露，暂不改）：`circuit_breaker.py` 的
`except Exception` 把永久性错误（如 403 计费/鉴权）与瞬时故障同等计入熔断，
未配置 fallback 时会话落到 `failed` 且回复为空，而不是转人工。
同文件对 `ContextWindowExceeded` 已有"非 provider 故障不污染熔断"的先例可参照。

## 已完成：可靠投递（事务发件箱）

原优先级一。消息、会话与待投递事件同事务落库，独立 relay 补投，三条验收全部满足：

- 队列短暂不可用后仍能补投：`scripts/e2e_outbox_recovery.py` 把 API 的 broker
  指向不可达地址，验证请求仍返回 200、事件留在 pending、relay 恢复后补投成功；
  已接入 CI（“Outbox reliable-delivery proof”）。
- 重复投递不会重复处理业务：投递语义是 at-least-once，重复消费由
  `runner._claim_session` 的 CAS（只允许 queued/failed/timeout 进入 processing）
  兜成幂等 no-op；e2e 断言补投后 agent 回复恰好 1 条。
- 有积压数量和失败告警：`/api/admin/metrics` 暴露 `outbox.pending`、`outbox.stuck`
  （连续失败达阈值）与 `oldest_pending_age_sec`；relay 在事件达到阈值时打 ERROR 日志。

relay 刻意做成独立进程而非 Celery beat 定时任务——beat 自身也要把调度消息投进
broker，用 broker 去救 broker，在 broker 宕机时同样失效。

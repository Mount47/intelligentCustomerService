# 请求处理链路

## 一条消息如何进入系统

```text
用户发送消息
→ 校验登录凭证
→ 以登录身份覆盖请求中的用户编号
→ 校验订单和工单归属
→ 按用户限流
→ 根据客户端消息编号去重
→ 写入工单消息
→ 创建智能体会话
→ 提交数据库事务
→ 投递消息队列
→ 立即返回会话编号
```

接口不会同步等待大模型完成，因为模型调用可能持续数秒。请求先快速落库和入队，工作进程
按照自身处理能力消费任务，可以避免高峰请求同时压到模型服务。

## 身份与资源归属

接口以登录凭证中的用户身份为准。即使请求正文传入其他用户编号，也会被拒绝或覆盖。

绑定订单和已有工单时还会检查：

- 订单是否存在；
- 订单是否属于当前用户；
- 工单是否属于当前用户；
- 工单是否已经绑定另一张订单。

这一步阻止用户通过修改编号访问他人资源。

## 消息去重

客户端为消息提供稳定的消息编号。系统先做快速查询，真正的并发正确性由
`用户编号 + 客户端消息编号` 的数据库唯一约束保证。

两个请求同时到达时，可能都在查询阶段看不到旧记录，但数据库只允许一个事务成功。
失败方回滚到保存点后查询胜出的会话并返回。

## 入队与本地模式

- 完整环境使用 Redis 与 Celery；
- 本地开发可以使用后台线程；
- 两种方式最终都调用同一个智能体运行器。

当前仍存在数据库提交成功但队列投递失败的短暂窗口。更严格的生产实现可以增加“事务事件表”，
让数据库事务同时写入待投递事件，再由独立投递程序可靠发送。

## 结果获取

前端优先通过带登录凭证的服务端事件流获取完整会话状态变化；连接失败时退回定时查询。

这里推送的是：

- 任务状态；
- 识别意图；
- 选中技能；
- 工具调用摘要；
- 最终回复；
- 令牌和耗时。

它不是逐字生成流，也不暴露模型隐藏思维。

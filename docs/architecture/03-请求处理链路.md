# 请求处理链路

## 一条消息如何进入系统

```text
用户发送消息
→ 校验登录凭证
→ 以登录身份覆盖请求中的用户编号
→ 校验订单和工单归属
→ 按用户限流
→ 根据客户端消息编号去重
→ 写入工单消息
→ 创建智能体会话
→ 写入待投递事件（与上面两步同一个事务）
→ 提交数据库事务
→ 投递消息队列（内联快路；失败则留给补投程序）
→ 立即返回会话编号
```

接口不会同步等待大模型完成，因为模型调用可能持续数秒。请求先快速落库和入队，工作进程
按照自身处理能力消费任务，可以避免高峰请求同时压到模型服务。

## 身份与资源归属

接口以登录凭证中的用户身份为准。即使请求正文传入其他用户编号，也会被拒绝或覆盖。

绑定订单和已有工单时还会检查：

- 订单是否存在；
- 订单是否属于当前用户；
- 工单是否属于当前用户；
- 工单是否已经绑定另一张订单。

这一步阻止用户通过修改编号访问他人资源。

## 消息去重

客户端为消息提供稳定的消息编号。系统先做快速查询，真正的并发正确性由
`用户编号 + 客户端消息编号` 的数据库唯一约束保证。

两个请求同时到达时，可能都在查询阶段看不到旧记录，但数据库只允许一个事务成功。
失败方回滚到保存点后查询胜出的会话并返回。

## 入队与本地模式

- 完整环境使用 Redis 与 Celery；
- 本地开发可以使用后台线程；
- 两种方式最终都调用同一个智能体运行器。

## 可靠投递（事务发件箱）

数据库提交成功、但队列投递失败，会让会话永远停在排队状态，用户再也等不到回复。
这不是理论风险，而是用户可见的丢消息。

做法是把待投递事件和消息、会话写在同一个事务里：

```text
同一事务写入消息、会话、待投递事件
→ 接口提交后内联投递一次（快路，不牺牲延迟），成功则把事件标记为已发送
→ 投递失败时事件留在待发送状态，接口照常返回成功
→ 独立补投程序轮询待发送事件，指数退避重投，成功后标记完成
```

几个关键选择：

- 补投程序是独立进程，不是队列的定时任务。定时任务本身也要把调度消息投进队列，
  用队列去救队列，在队列宕机时同样失效；补投程序只依赖数据库。
- 投递语义是至少一次。重复投递是安全的，因为运行器抢占会话时使用条件更新，
  只有排队、失败、超时状态能进入处理中，重复消费自然成为空操作。
- 取件使用行锁并跳过已锁定行，多个补投实例不会重复取同一条事件。
- 事件带唯一去重键，同一会话只会有一行，重试路径不会把同一事件写进去两次。

积压与失败通过管理端指标暴露：待发送数量、连续失败达到阈值的数量、最旧待发送事件的年龄。

## 结果获取

前端优先通过带登录凭证的服务端事件流获取完整会话状态变化；连接失败时退回定时查询。

这里推送的是：

- 任务状态；
- 识别意图；
- 选中技能；
- 工具调用摘要；
- 最终回复；
- 令牌和耗时。

它不是逐字生成流，也不暴露模型隐藏思维。

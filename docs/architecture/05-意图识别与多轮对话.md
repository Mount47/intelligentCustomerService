# 意图识别与多轮对话

## 结构化意图

系统不会只返回一个字符串标签，而是生成结构化结果：

- 意图；
- 肯定、否定、疑问或中性语气；
- 查询、执行、取消、确认等动作类型；
- 置信度；
- 是否需要二次确认；
- 判断原因。

## 识别流程

```text
规则召回候选
→ 判断否定和疑问
→ 生成结构化意图
→ 无法确定时带历史交给模型分类
→ 仍不确定则澄清
```

关键词只用于召回候选，不能直接触发业务动作：

- “我要退款”是退款申请；
- “能退款吗”是政策咨询；
- “我不想退款了”是取消；
- “确认”只有在等待确认状态下才有业务含义。

## 为什么保留规则快路

- 高频明确表达响应快、成本低；
- 确认和取消等高风险信号可以更严格；
- 自动化测试容易覆盖；
- 模型故障时仍保留基本能力。

规则不能覆盖全部表达，因此长尾语义交给模型兜底，但模型输出必须严格解析并检查是否属于允许枚举。

## 缺信息续接

技能发现缺少订单号时，不只把工单改成“等待信息”，还会保存：

- 原意图；
- 原技能；
- 待补字段；
- 已收集字段；
- 原结构化意图。

下一轮先判断用户是否在补充信息，还是提出了明确的新意图。新意图可以打断旧流程。

## 退款确认

网页端优先显示结构化操作卡片：确认需要两次点击，取消一次点击。第二次确认通过
`POST /api/chat/action` 提交，后端校验登录用户、工单状态、动作编号、订单和金额后，
再进入专用确认处理链路。文本确认仍作为旧客户端兼容路径：

- 明确确认：继续；
- 明确取消：取消；
- 迟疑或无关回答：保持等待并重新提示；
- 待确认动作不存在、过期或订单不匹配：拒绝执行。

这是失败时偏向安全的设计。

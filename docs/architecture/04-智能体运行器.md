# 智能体运行器

## 它解决什么问题

智能体核心负责“怎么思考和调用工具”，运行器负责“这次任务怎样安全地开始、恢复、提交和失败”。
如果没有运行器，模型循环很容易与队列、数据库事务和重试逻辑混在一起。

## 执行步骤

```text
读取智能体会话
→ 原子抢占可处理状态
→ 精确读取触发消息
→ 读取工单状态和版本
→ 恢复历史、待确认动作和待补信息
→ 组装智能体上下文
→ 调用智能体核心
→ 写入智能体回复
→ 比较工单状态和版本
→ 同一事务提交回复、业务副作用和状态
→ 更新会话结果
→ 触发独立质量检查
```

## 原子抢占

消息队列采用“处理完成后确认”的方式。工作进程可能在业务事务提交后、确认消息前退出，
队列随后会重新投递同一个任务。

运行器只允许以下状态进入处理中：

```text
排队中、失败、超时 → 处理中
```

已经完成、等待用户输入或已转人工的会话再次投递时直接忽略，避免重复回复和重复副作用。

## 精确消息绑定

运行器使用会话保存的 `source_message_id` 读取触发消息，并再次验证消息的工单、用户和发送者。
只有迁移前的历史数据才退回“读取最新用户消息”的兼容逻辑。

## 上下文恢复

只有等待确认和等待补充信息的工单状态会恢复到下一轮。其他状态收到新消息时按新请求处理。

恢复内容包括：

- 当前工单和订单；
- 当前用户消息；
- 这条消息之前的对话历史；
- 待确认动作；
- 待补信息上下文。

## 事务与版本比较

运行器在调用智能体前记住工单状态和版本，最终执行：

```text
只有数据库中的状态和版本仍等于读取值，才更新为目标状态。
```

如果更新失败，说明别的工作进程已经推进了工单。当前事务整体回滚，因此本次回复、退款申请、
派生工单和状态变化都不会残留。

## 失败处理

出现异常时：

1. 先回滚智能体和业务服务产生的全部未提交变化；
2. 重新读取智能体会话；
3. 标记失败或超时并记录错误；
4. 完整队列模式将异常交给有限重试；
5. 达到重试上限后保留失败状态供人工排查。

## 与智能体循环的区别

| 智能体运行器 | 智能体循环 |
|---|---|
| 管理任务和数据库事务 | 管理模型和工具交互 |
| 恢复跨轮状态 | 解析模型工具调用 |
| 处理重复投递 | 执行技能允许的工具 |
| 防止旧状态覆盖 | 将工具结果返回模型 |
| 保存最终结果 | 产出业务决策所需信息 |

# 业务与数据模型

## 为什么先学数据模型

智能体收到的是自然语言，但真正可信的业务事实来自数据库。订单号、金额、订单归属、
退款状态和工单状态不能依赖模型记忆或对话摘要。

## 核心实体

```text
用户
├─ 订单
│  ├─ 商品明细
│  ├─ 物流
│  └─ 退款申请
└─ 工单
   ├─ 工单消息
   ├─ 状态变更记录
   ├─ 智能体会话
   │  ├─ 工具调用记录
   │  └─ 质量记录
   └─ 服务时限记录

知识文档独立保存售后政策
```

当前表数量以 [项目状态](项目状态.md) 为准。

## 三个容易混淆的对象

### 工单

工单表示一项业务处理过程。它保存业务状态、关联订单、待确认动作、待补信息和版本号。
用户多轮对话可以继续使用同一工单。

### 工单消息

工单消息保存用户、智能体、人工客服和系统的发言。用户消息携带客户端消息编号，用于
防止网络重试导致同一消息重复处理。

### 智能体会话

智能体会话表示“处理某一条用户消息的一次任务”。它保存：

- 精确触发消息；
- 排队、处理中、完成、失败等任务状态；
- 本次识别的意图和技能；
- 模型名称、令牌数量和估算成本；
- 开始、完成时间与错误信息。

不能把这三个对象合并，因为业务工单、多轮消息和异步任务的生命周期不同。

## 关键字段

### `source_message_id`

每个智能体会话精确绑定触发它的用户消息。工作进程不能简单读取“最新用户消息”，否则
并发消息可能被错误配对。

### `version`

工单使用版本号进行比较后更新。工作进程只有在状态和版本仍与读取时一致时才能提交结果，
防止较慢的旧任务覆盖较新的状态。

### `pending_action`

保存等待用户确认的危险动作，包括动作编号、退款或退货类型、订单、金额和创建时间。
网页按钮提交时必须逐项匹配，不能只看到“确认”两个字就执行。

### `pending_context`

保存缺少信息时的原意图、技能、待补字段和已收集字段。它负责跨轮恢复“刚才要办什么”。

### 退款唯一键

退款申请同时保存：

- 客户端幂等键；
- 请求参数指纹；
- 业务去重键；
- 数据库唯一约束。

它们分别解决请求重试、同键不同参数、业务语义重复和真实并发竞争。

## 数据设计原则

- 身份、金额、状态等硬事实从数据库读取；
- 对话摘要只保存软上下文；
- 业务状态与任务状态分开；
- 状态变化既写当前值，也保留历史记录；
- 资金类操作的最终唯一性由数据库承担；
- 审计记录与主业务记录分开保存。

## 1. 定位与 v1 目标

电商售后智能客服工单 Agent。v1 只做**退款 + 物流**两条链路，把 4 个硬模块做透：
退款三层幂等 / 异步轮询最终一致 / 工单状态机 / 规则评测+guardrails 对抗。

链路本质：`意图识别 → 业务状态判断 → 工具调用(LLM 规划) → 工单状态流转 → 自动解决或人工升级 → 质检/指标`。
非目标：陪聊。Agent 的每个对外动作都必须基于工具结果或知识库，不得编造。

**v1 质量度量取舍**：做 `app/eval`（评测集 + run_eval + metrics，含 guardrails 对抗指标）和 `observability/metrics`（运行时指标）；**不做完整 QualityReviewSkill**（会话级 LLM 质检评分）。`quality_reviews` 表建好但 v1 不写入，结构留给后续迭代。

## 2. 技术栈

- Python 3.11+ / FastAPI / Pydantic v2 / SQLAlchemy 2.x

## 3. 系统架构（分层）

```
 用户/客户端
   │ HTTP
   ▼
┌─ API 层 (app/api) ─────────────────────────────────────────┐
│ POST /chat/message → 落库+建session+入队，立即返回(不阻塞)   │
│ GET  /chat/session/{id} → 轮询 task_status + latest_reply   │
│ tickets / admin / health                                    │
└───────────────┬────────────────────────────────────────────┘
                │ enqueue(session_id)   [Redis broker]
                ▼
┌─ 异步任务层 (app/workers) ─────────────────────────────────┐
│ process_agent_message: 限流消费，retry/timeout              │
└───────────────┬────────────────────────────────────────────┘
                ▼
┌─ Agent 核心层 (app/agent) ─── harness/执行管道 ────────────┐
│ IntentClassifier(规则快路+LLM兜底) → SkillRouter            │
│ → Skill 只产出 SkillPlan(系统提示+工具白名单+完成策略)      │
│ → **AgentCore harness 统一跑 LLM 工具调用循环(ReAct)** ──┐  │
│        每次工具调用前后：Guardrails + StateMachine 闸门  │  │
│ → Skill.finalize → Decision；ResponseGenerator(受guardrails)┘│
│ → 落 token/cost + tracing                                   │
└──────┬─────────────────────┬──────────────────┬────────────┘
       │ 只经 tool/service    │                  │
       ▼                      ▼                  ▼
 工具层(app/tools)     业务服务层(services)   LLM抽象(app/llm)
 结构化dict+审计      order/logistics/        Claude适配器
                     refund/ticket/sla/      (可换 OpenAI/本地)
                     knowledge
       └──────────────┬───────────────────────────┘
                      ▼
            PostgreSQL（11 表）+ 可观测落库
```

铁律：
- **API 不阻塞**等 Agent；只落库+入队+查询。
- **Agent 不碰 DB**，只经 tool / service。
- **状态机集中**在 StateMachine，Skill 不自己改状态（只声明 `next_state`）。
- **危险工具**（create_refund_draft / handoff）经 harness 闸门，LLM 不能盲目触发不可逆动作。

## 5. Agent 执行链路与契约 ★（脊椎，M2/M3 照此写）

### 5.1 AgentContext（贯穿所有步骤）
```python
@dataclass
class AgentContext:
    session_id: int
    ticket_id: int
    user_id: int
    message: str
    order_id: int | None
    intent: str | None = None
    skill: str | None = None
    state: str | None = None          # 当前工单状态
    tool_call_records: list[ToolCallRecord] = field(default_factory=list)  # 每次工具调用的完整记录(便于 tracing/落 agent_tool_calls)
    history: list[Msg] = field(default_factory=list)
    token_acct: TokenAcct = ...        # 累计 prompt/completion/cache/cost
    decision: "Decision | None" = None
```

### 5.2 Skill 接口（声明式，**不自己跑 ReAct loop**）
Skill 只描述"该怎么做"，不执行循环。ReAct loop 由 AgentCore harness 统一跑（见 5.4），
保证 guardrails / 状态机闸门 / 工具审计 / token 记账在一处统一实施，不散落各 Skill。
```python
class Skill(Protocol):
    name: str
    triggers: set[str]                       # 触发的 intent
    def plan(self, ctx: AgentContext) -> "SkillPlan": ...     # 产出本轮计划，不调 LLM/tool
    def finalize(self, ctx: AgentContext) -> "Decision": ...  # loop 结束后据 tool_call_records 产出决策

@dataclass
class SkillPlan:
    system_prompt: str                       # 该 Skill 的指令(可加载 instructions.md)
    allowed_tools: list[str]                 # 工具白名单(harness 据此约束 LLM 可调工具)
    max_iterations: int = 6                  # loop 上限，防失控
    required_info: list[str] | None = None   # 缺信息时先向用户索取(短路 loop)

@dataclass
class Decision:
    reply: str                               # 对用户的回复（已过 guardrails）
    next_state: str                          # 交给 StateMachine.transition
    need_handoff: bool = False
    handoff_reason: str | None = None
    required_info: list[str] | None = None
```

### 5.3 Tool 契约（统一返回 + 自动审计）
```python
class ToolResult(TypedDict):
    ok: bool
    data: dict | None
    error: dict | None      # {code, message}；ok=False 时填

@dataclass
class ToolCallRecord:        # harness 每次调用工具后追加到 ctx.tool_call_records
    tool_name: str
    input_json: dict
    result: ToolResult
    success: bool
    latency_ms: int
    error_message: str | None = None
# 约定：
# - 所有 tool 返回 ToolResult；失败不抛、不崩主流程
# - harness 每次调用生成 ToolCallRecord，落 agent_tool_calls 表 + 进 ctx.tool_call_records
# - 危险/写操作 tool 内做权限校验 + 幂等
```

### 5.4 单条消息 pipeline（harness）
```
1 收消息 → 消息幂等去重(见 §9) → save ticket_messages
2 创建/读取 ticket + agent_session(queued)
3 [worker] session=processing
4 IntentClassifier: 规则快路命中→intent；否则 LLM 兜底
5 SkillRouter: intent → Skill（无匹配→general/out_of_scope）
6 读当前 ticket 状态；plan = Skill.plan(ctx)
   - 若 plan.required_info 有缺：短路 loop，直接索取信息 → waiting_user_input
7 **AgentCore harness 统一跑 ReAct loop**（用 plan.system_prompt + plan.allowed_tools）
     while stop_reason == tool_use and iter < plan.max_iterations:
        LLM 提议 tool_use（仅限 allowed_tools）
        → Guardrails.precheck(tool, args)         # 危险动作拦截/降级
        → StateMachine.can_run(tool, state)       # 状态合法性
        → tool 执行(权限+幂等) → ToolCallRecord 追加 ctx + 回灌 LLM
8 decision = Skill.finalize(ctx)  # 据 tool_call_records 产出 reply/next_state/handoff
9 Guardrails.postcheck(decision.reply)            # 禁承诺退款/赔偿/送达时间…
10 StateMachine.transition(ctx.state → decision.next_state)  # 集中、记日志、非法抛异常
11 写 Agent reply 到 ticket_messages；更新 session(final_status, token/cost)
12 用户 GET /chat/session 轮询取结果

注：reply 既可由 Skill.finalize 用模板/裁剪产出，也可由 LLM 在 loop 末轮自然生成；
两条路都经第 9 步 guardrails postcheck，绝不绕过。
```

### 5.5 多轮 loop（跨消息）
由**状态机 + agent_session** 承载：`waiting_user_input` 态下用户再发消息 → 从上次状态续走。不靠进程内存。

### 5.6 走通顺序（walking skeleton）
M1 后先做一个端到端空壳：假 intent→假 Skill 返回 canned 回复→假状态推进，证明脊椎通；M2/M3 再按上述契约填真 tool/service；M4/M5 实体化。

## 6. LLMClient 抽象层（provider 可插拔）

```python
class LLMClient(Protocol):
    model_name: str
    def chat(self, *, system: str, messages: list[Msg],
             tools: list[ToolSpec] | None = None,
             stream: bool = False) -> "LLMResponse": ...

@dataclass
class LLMResponse:
    text: str
    tool_calls: list[ToolCall]         # 规整成 provider 无关结构
    stop_reason: str                   # end_turn | tool_use | max_tokens | refusal
    usage: Usage                       # prompt/completion/cache_read/total tokens
```
- 适配器：`ClaudeAdapter`（anthropic SDK，`thinking:{type:"adaptive"}`，长输出 streaming，prompt caching 缓存 system+政策前缀）；预留 `OpenAICompatAdapter`。
- `registry.py` 按 `settings.LLM_PROVIDER` 选适配器；**模型名/key/base_url 全走 .env，代码内不写死**（`LLM_MODEL` 注入适配器，`model_name` 仅运行时读取）。
- 切 provider/模型 = 改 .env，不动代码；token/cost 也据 `.env` 的模型价目折算。
- 能力下限：必须支持 tool calling；usage 缺字段时按 0 记并标 `cache_hit=False`。
- cost：各 provider 价目放 config，`estimated_cost = Σ tokens × 单价`。

## 7. 工单状态机

正常态：
`created → intent_detected → info_required → info_collected → tool_executing
→ waiting_user_confirm → resolved_by_agent | need_human → resolved_by_human | rejected → closed`

异常态：`tool_failed / policy_conflict / user_angry / refund_high_risk / sla_timeout`

约束：
- 单一 `StateMachine`，声明合法转移表 `TRANSITIONS: dict[str, set[str]]`。
- 非法转移抛 `InvalidStateTransition`；每次转移写日志（tracing）。
- 高风险禁止直达 `resolved_by_agent`，强制 `need_human` / `waiting_user_confirm`。
- 转移只在 pipeline 第 10 步集中执行，Skill 仅声明 `next_state`。

### 7.1 转人工（`need_human`）条件 ★
原则：**不可逆/高风险 + 超出 Agent 能力 + 用户主动 + 系统出错 → 一律升级人工**（没把握就交人，不赌、不硬刚、不乱退）。

| 类别 | 触发 | handoff_reason |
|---|---|---|
| 用户主动/情绪 | 明确要人工("人工/转人工/客服")、投诉("投诉/质量问题/坏了/破损/假货") | `human_handoff` / `product_complaint` |
| 退款高风险 | 金额 > `refund_high_amount_threshold`(默认500) / 特殊商品(生鲜·定制) / 已签收 > `refund_return_window_days`(默认7天) | `refund_high_risk` |
| 校验失败 | 订单不存在 / 非本人 / 状态不可退(如已取消) / 已有人工审核中退款 | `order_not_found` / `not_owner` / `not_eligible` / `refund_in_progress` |
| 物流异常 | 显示签收但未收到 / 查不到物流 | `delivered_not_received` / `logistics_not_found` |
| 系统兜底 | 缺工具上下文/系统异常 | `no_tool_context` |

阈值配置化（`config.py`）；与 `failed`/`timeout`（worker 任务失败重试）区分——后者非业务人工升级。

## 9. 幂等（两类，别混）

**两类幂等分开，不共用一个 hash(content)：**

### 9.1 消息幂等（接入层，防重复处理同一条消息）
- 防止前端重试/重复点击导致同一条用户消息被处理两次、建出两个 session。
- 客户端在 `POST /chat/message` 头/体带 `message_id`（或 request-id）；服务端以
  `UNIQUE(user_id, message_id)` 去重——重复请求直接返回已有 `session_id/ticket_id`。
- 仅保证"同一条消息只处理一次"，**与退款业务正确性无关**，不参与退款唯一约束。

### 9.2 退款业务幂等（ADR-4，三层）
1. **客户端 `idempotency_key`** + **`request_hash`**（= 退款关键参数指纹：order_id+amount+reason_normalized）。
   客户端可传 idempotency_key；不传则服务端据退款业务字段生成。`request_hash` 用于判同 key 是否同请求。
2. **服务端 `business_key`** = `hash(user_id + order_id + "refund" + reason_normalized)`。防 Agent/LLM 重试产生重复业务动作。
3. **DB 唯一约束**：`UNIQUE(user_id, idempotency_key)`、`UNIQUE(business_key)`；`INSERT ... ON CONFLICT` / 捕 `IntegrityError` 回查。并发兜底，只成功一条。

语义：
- 同 `(user_id, idempotency_key)` 且 `request_hash` 一致 → 返回已有 `refund_request_id`（幂等命中）。
- 同 `(user_id, idempotency_key)` 但 `request_hash` 不一致 → `409 IDEMPOTENCY_KEY_CONFLICT`。
- 同 `business_key` 命中 → 返回已有 `refund_request_id`。
Redis SETNX 仅短期防抖锁，**不作正确性保证**。
高金额(>阈值)/生鲜/定制/超售后期→不自动退款，建人工审核工单。
必有并发测试：两个相同退款并发进，断言 `refund_requests` 只多一条。

## 10. 异步轮询闭环（ADR-5）

`task_status`: `queued → processing → {completed | waiting_user_input | need_human | failed | timeout}`
`GET /chat/session/{id}` 返回：session_id/ticket_id/task_status/current_intent/current_skill/current_state/latest_reply/final_status/error_message/retry_count/created_at/started_at/finished_at。
Worker：retry（指数退避）；超时标 `timeout`/`need_human`；绝不让 API 等。SSE/WebSocket 列后续。

## 11. Guardrails（作用于真实 LLM 输出）

三层：①结构化输出/系统提示约束 ②工具调用 precheck（危险动作拦截/降级）③回复 postcheck。
规则：禁承诺一定退款/赔偿；禁承诺送达时间(除非物流工具返回)；高金额/生鲜/定制退款必人工确认；情绪激烈优先转人工；置信度低/工具失败/知识库缺失→拒答或转人工，不编造。
验证：评测集放 ≥5 条对抗样例（诱导承诺退款/赔偿/绕过订单校验/退非本人账户/情绪威胁），量化 `forbidden_phrase_block_rate / policy_compliance_rate / high_risk_handoff_accuracy / unsupported_claim_rate`。

## 12. RAG / 知识库

v1 关键词检索（`search_policy_docs`），文档带 `category/version`。回答政策尽量引用来源；无答案→拒答或转人工。向量检索列后续。

## 13. 约定

- **命名**：表/字段 snake_case；intent/state/status 用小写下划线常量；tool 函数动词开头（`get_/check_/create_/update_`）。
- **配置**：全放 `.env`（DB/Redis URL、`LLM_PROVIDER`、模型/key/base_url、退款阈值、SLA 时长）。`core/config.py` 用 Pydantic Settings。
- **异常**：DB/Redis/LLM 连接均有异常处理；自定义异常在 `core/exceptions.py`。
- **日志/tracing**：关键流程、状态转移、工具调用、token/cost 全落。
- **分层纪律**：API→service/worker；Agent→tool/service；只有 service/tool 碰 DB。
```

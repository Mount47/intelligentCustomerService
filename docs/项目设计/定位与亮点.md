# 定位与亮点（面试/展示底稿）

> 用途：讲清"这不是又一个会聊天的客服机器人"。每条亮点都能指到具体代码。
> 配套：范围见 [SupportFlow 范围]/STATUS，决策见 DECISIONS，踩坑见 实际问题与解决.md。

---

## 一句话定位

> **一个把"退款"这类高危售后事务做到【安全、幂等、可审计、可评测】的 Agent —— 不是又一个 RAG 聊天客服。**

核心理念：**把 LLM 当一个【有界组件】**，只用它做"理解/解释"这类 LLM 擅长的事；**不可逆/关键决策由确定性代码把关**，而不是什么都交给 LLM。

---

## 对标：烂大街聊天 Agent vs 本项目

**烂大街 = RAG + LLM 会聊天**：FAQ 问答、政策检索、多轮闲聊、调 API 查单再复述。
**天花板**：一切流经 LLM、由 LLM "决定+执行+生成"。短板——LLM 直接做不可逆动作(危险)、零幂等(重复退款)、乱传参数(越权)、乱承诺、黑盒不可审计、demo 好看但无可量化质量。

> 它是"一个会聊天、但愿能做对事的 LLM"；本项目是"用了 LLM 的工程化事务系统"。

| 维度 | 烂大街聊天 Agent | 本项目 |
|---|---|---|
| 不可逆动作 | LLM 直接执行退款 | **读写分离**：LLM 只读，退款由 finalize 确定性执行 |
| 重复/并发 | 重试即重复退款 | **三层幂等** + 会话级幂等（同订单不重复建草稿） |
| 安全 | LLM 传啥参数都执行 | **参数绑定**：user_id/order_id 服务端强绑，防越权(IDOR) |
| 高危确认 | 一句话就退 | **确认门** + 否定/疑问识别（"我不想退款了"不会误退）* |
| 流程状态 | 无状态闲聊 | **状态机**：工单生命周期、合法流转 |
| 合规 | 可能乱承诺 | **guardrails**：禁语拦截、不承诺退款/赔偿 |
| 承载 | 同步玩具 | **异步队列 + worker + 轮询**，可削峰 |
| 可观测 | 黑盒 | **trace_id 全链路 + 工具调用审计 + token/成本记账** |
| 质量 | "demo 看着行" | **评测管线**：断言层 + LLM-as-Judge + 回归 |
| 人机协作 | "我帮不了" | **转人工** + 会话摘要交接* |

\* 标星为设计/进行中，见末尾"诚实边界"。

## 五大亮点（每条配一句 pitch + 代码位置）

### 1. 不可逆动作不交给 LLM（读写分离）
- **讲法**："我没把退款交给 LLM——它在 loop 里只读取信息，退款决策与写操作由 `finalize` 确定性代码执行。不可逆动作不赌模型。"
- **代码**：`skills/refund_handling/handler.py`（finalize）、`agent_core.handle`（loop 只读 → finalize 写）。

### 2. 能证明不会重复退款（幂等）
- **讲法**："三层幂等——客户端键 → 业务键 → DB 唯一约束兜底(IntegrityError 回查)；并发实测只成一条。再加会话级幂等：同订单跨对话轮次反复触发也不重复建草稿。"
- **代码**：`services/refund_service.create_refund_draft`、`get_active_refund`；`tests/test_concurrency.py`、`test_refund_idempotency.py`。

### 3. LLM 改不了它该用哪个订单（参数绑定 / 防越权）
- **讲法**："工具的 user_id/order_id 由服务端用会话真值强制绑定，覆盖 LLM 所填。LLM 被诱导传他人 id 也无效——这是防越权访问(IDOR)，prompt 约束根本防不住。"
- **代码**：`agent_core._bind_context_args`、`tools/base.ToolRegistry.schema_props`；`tests/test_agent_loop.test_context_binding_overrides_llm_args`。

### 4. 每次改动跑回归，有数据不靠感觉（评测）
- **讲法**："评测分两层——代码断言验流程(意图/路由/工具/状态机/转人工)，LLM-as-Judge 验回复语义质量(盲评+参考答案锚定)。stub 可复现进 CI，--real 用真实模型。而且我诚实标注评测边界。"
- **代码**：`eval/run_eval.py`、`eval/judge.py`、`eval/test_cases.json`(30+5)。

### 5. 出问题能定位到哪一步（可观测）
- **讲法**："每会话一个 trace_id 串全链路，steps 时间线 + 工具调用审计(入参/出参/成功/耗时)全落库，token 与成本可计费。黑盒变白盒。"
- **代码**：`observability/tracing.py`、`tools/base`(自动写 agent_tool_calls)、`agent_sessions`(token/cost 字段)。

> 这五句，烂大街的 RAG 聊天机器人一句都说不出来。

## 战略定位（怎么取舍）

- **不在"广度"上卷**：RAG 堆 FAQ 谁都会，卷不过也没价值。
- **在"高危事务的正确性/安全/可审计/可评测"上立住**：范围收窄到 退款·退货·物流·转人工 + 政策答疑，把核心做到生产级深度。
- **深度 > 广度**：3-4 个场景做到极致，胜过 10 个浅功能。

## 诚实边界（可信度来自不吹）

- **已立住**：读写分离、三层幂等(顺序+sqlite；PG 真并发待补一次实测)、参数绑定/防越权、guardrails、状态机、异步削峰、可观测、评测+LLM-Judge、P1 对话记忆。
- **进行中/规划**：退款确认门 + 否定/疑问意图(已设计)、转人工会话摘要(TODO-1)、out_of_scope 硬护栏(#6)、PG 端到端真实并发实测。
- **明确不做**：售前/购物、商品明细(无 order_items 表)、账户/支付/改单、真正打款。超范围 → 礼貌引导/转人工。

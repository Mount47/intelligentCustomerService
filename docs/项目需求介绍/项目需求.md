你现在是一名资深后端架构师 + Agent 工程师，请帮我从 0 设计并实现一个“面向电商售后的智能客服工单 Agent 系统”，项目名称为 SupportFlow。

这个项目不是普通 FAQ 问答机器人，而是一个具备业务流程、工具调用、工单状态机、人工升级、SLA 监控、质检评分、异步任务、高并发消息接入和可部署压测能力的单 Agent 项目。目标是做成可以写进简历、可以部署、可以压测、可以被面试官深挖的 Agent 工程项目。

一、项目定位

SupportFlow 用于解决电商售后场景中人工客服响应慢、重复劳动多、业务规则执行不一致、工单质检困难、高峰期消息并发压力大等问题。

系统需要支持以下典型售后场景：

1. 订单查询
2. 物流查询
3. 物流异常催件
4. 退款申请
5. 退货申请
6. 发票申请
7. 优惠券问题
8. 商品质量投诉
9. 人工客服升级
10. 会话结束后的自动质检评分

核心目标不是让 Agent 陪用户闲聊，而是让 Agent 完成：

意图识别 → 业务状态判断 → RAG 知识检索 → 工具调用 → 工单状态流转 → 自动解决 / 人工升级 → 质检评分 → 指标记录。

三、项目总体架构

请按照以下分层设计：

1. API 层
   负责接收用户消息、创建工单、查询工单、查看会话记录、管理员质检查看等。

2. Agent 核心层
   负责意图识别、Skill 路由、状态机推进、工具调用规划、回复生成、人工升级判断。

3. Skill 业务流程层
   封装高频售后流程，例如退款处理、物流异常、投诉安抚、发票申请、质检评分。

4. Tool / MCP 工具层
   封装订单、物流、退款、工单、知识库等外部系统能力。第一阶段可以先用普通 Python 工具函数，第二阶段再封装为 MCP Server 风格。

5. 业务服务层
   负责订单、工单、SLA、退款规则、用户权限、审计日志等业务逻辑。

6. 数据层
   使用 PostgreSQL 存储用户、订单、物流、工单、会话消息、工具调用日志、质检结果、SLA 记录等。

7. 异步任务层
   使用 Redis + Celery/RQ 解耦用户消息接入和 Agent 推理任务。用户请求不能阻塞等待 LLM 完整处理。

8. 可观测层
   记录 agent_sessions、agent_tool_calls、ticket_messages、quality_reviews、latency、token_cost、error_stack 等信息。

七、Agent 核心逻辑

Agent 每次处理用户消息时，请按照以下流程：

1. 接收用户消息
2. 保存消息到 ticket_messages
3. 创建或读取 agent_session
4. 识别 intent
5. 根据 intent 选择 Skill
6. 检查当前 ticket 状态
7. Skill 执行业务流程
8. Skill 调用工具
9. 工具返回结构化结果
10. Agent 根据结果生成回复
11. 判断是否解决、是否转人工、是否需要补充信息
12. 更新 ticket 状态
13. 记录 tool calls 和 tracing
14. 返回结构化结果
15. 会话结束后触发 QualityReviewSkill

九、Skill 设计

请实现以下 Skill。

1. RefundHandlingSkill

触发 intent：

* refund_request
* return_request

流程：

1. 检查是否有 order_id
2. 没有 order_id 时询问用户补充订单号
3. 调用 get_order_detail
4. 调用 check_refund_policy
5. 如果 eligible=true 且 risk_level=low，创建退款草稿
6. 如果 require_human_approval=true，创建工单并转人工
7. 生成用户回复
8. 更新工单状态

人工升级规则：

* 订单金额大于 500
* 商品类型为 fresh_food 或 customized_product
* 已签收超过 7 天
* 用户情绪为 angry
* 退款规则不明确
* 工具调用失败

2. LogisticsExceptionSkill

触发 intent：

* logistics_query
* logistics_exception

流程：

1. 获取 order_id

2. 调用 get_logistics_status

3. 判断是否物流异常

4. 正常则返回物流状态

5. 如果超过 48 小时无更新，创建催件工单

6. 如果显示签收但用户未收到，转人工

7. 更新工单状态

8. ComplaintDeEscalationSkill

触发 intent：

* product_complaint
* human_handoff
* 用户情绪 angry

流程：

1. 识别情绪等级

2. 生成安抚回复

3. 不承诺超出售后政策的赔偿

4. 收集订单和问题信息

5. 创建高优先级投诉工单

6. 转人工

7. InvoiceRequestSkill

触发 intent：

* invoice_request

流程：

1. 获取 order_id

2. 检查订单是否可开票

3. 收集发票抬头、税号、邮箱

4. 创建发票申请工单

5. 返回处理状态

6. QualityReviewSkill

触发条件：

* 会话结束
* 工单状态为 resolved_by_agent / need_human / closed

输出：

* resolution_score
* tool_call_correctness
* policy_compliance

二十三、必须补充的生产级设计约束

1. 退款幂等机制

退款场景必须实现幂等控制，不能因为用户重复点击、前端重试、Agent 重试或并发请求导致重复创建退款申请。

请设计并实现三层幂等：

* 客户端 idempotency_key：用于防止用户重复点击和网络重试。
* 服务端 business_key：根据 user_id、order_id、action_type、refund_reason_normalized 生成，用于防止 Agent 重试产生重复业务动作。
* 数据库唯一约束：作为最终一致性兜底，确保并发情况下只有一个退款草稿创建成功。

Redis SETNX 可以作为短期防抖锁，但不能作为最终正确性保证。最终正确性必须由数据库唯一约束和事务保证。

create_refund_draft 工具要求：

* 同一个 idempotency_key 重复请求时，返回已有 refund_request_id。
* 同一个 business_key 重复请求时，返回已有 refund_request_id。
* 如果 idempotency_key 相同但请求参数不一致，返回 409 IDEMPOTENCY_KEY_CONFLICT。
* 高金额、特殊商品、已签收超过售后期等场景不能自动退款，只能创建人工审核工单。
* 所有退款相关调用必须写入 agent_tool_calls 和 refund_requests。
* 必须提供并发测试，模拟两个相同退款请求同时进入，验证只创建一条 refund_requests。

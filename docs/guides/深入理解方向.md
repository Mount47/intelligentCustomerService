> 用途：把 SupportFlow 按“产品入口 → 5 个技术方向 → 证据收口”钻到底。
> 配套：[分模块学习路线](分模块学习路线.md) 负责建立知识地图，
> [面试问答](../interview/面试问答.md) 负责最终表达，
> [实际问题与解决](../incidents/实际问题与解决.md) 负责真实问题事实。
> 真值优先级：**代码 + 当次实跑测试 > CI 配置/运行产物 > git log > 文档**。

## 0. 先纠正深挖顺序

原来的五个方向技术密度高，但直接从 Agent 编排开讲，容易退化成后端知识点清单。完整顺序应是：

**方向零（产品需求与主链路）→ 一（Agent 安全内核）→ 二（幂等并发）→ 三（意图对话）→ 五（质量可观测）→ 四（高并发可用）→ 最终方向（证据与边界）**

每个方向都必须连续回答同一组问题：

1. 它解决了哪个**真实业务风险**？
2. 没有它会出现什么**具体错误或损失**？
3. 它织入了哪条**主执行链路**，不是只定义了什么类？
4. 状态存在哪里，谁读、谁写、何时提交？
5. 并发、重试和进程崩溃时会怎样？
6. 失败策略是重试、降级、等待确认，还是 fail closed？
7. 哪个测试、运行日志或数据库结果证明它有效？
8. 它还没有解决什么，不能把什么指标混为一谈？

答不出第 3、4、7 问，通常只能说明“写过代码”；答不出第 8 问，通常是在把规划当成果。

## 1. 方向零 · 产品需求与主链路 ★所有技术深挖的前提

### 1.1 服务谁，解决什么

- **直接用户**：电商订单的售后用户；通过聊天入口查询本人订单、物流，发起退款/退货，投诉或要求人工。
- **运营用户**：admin 身份可看工单、会话、指标与转人工摘要；**还不是可接单、回复、解决、关闭的完整人工客服工作台**。
- **业务目标**：让高频、规则明确的售后事务自助闭环；高风险、越权、低置信或系统无法安全处理的事务转人工。
- **非目标**：做一个开放域聊天机器人，或让 LLM 自主执行动钱操作。

### 1.2 当前真正支持的业务

| 业务 | 当前主链路行为 | 性质 |
|---|---|---|
| 订单查询 | 查本人订单、状态和商品明细；无订单号可列单 | 只读业务动作 |
| 物流查询 | 查物流状态；已付款未发货时确定性说明备货中 | 只读业务动作 |
| 物流异常 | 超 48h 无更新建催件工单；签收未收到转人工 | 有副作用 |
| 退款/退货申请 | 低风险二次确认后建申请草稿；高风险建 `pending_human` 草稿并转人工 | 有副作用 |
| 退款咨询/取消 | 咨询只读；取消待确认动作或进行中申请 | 取消有副作用 |
| 投诉/明确人工 | 进入 `need_human` | 有状态副作用 |
| 发票/优惠券/通用政策 | GeneralSkill 兜底说明 | 浅支持，不是完整业务闭环 |
| 质检 | 有评测管线和 `quality_reviews` 表 | **没有会话结束后自动写质检表的主链路** |

注意：“只读业务动作”不代表 HTTP 请求不写库。`POST /chat/message` 无论问什么都会创建/复用 Ticket、写用户消息、建 AgentSession 并投递任务。

### 1.3 只读与副作用边界

- LLM loop 白名单只给查询类工具：订单、物流、政策、已有退款状态。
- 退款建单/取消、物流催件、Ticket 状态推进、SLA 回填由 Skill.finalize / service / runner 的确定性代码执行。
- 接入层副作用：消息落库、Ticket/Session 创建、Celery 投递。
- 状态落点：
  - 对话与任务：`ticket_messages`、`agent_sessions`
  - 流程状态与跨轮上下文：`tickets.status/version/pending_action/pending_context`
  - 退款正确性：`refund_requests` 双唯一约束
  - 工具审计：`agent_tool_calls`
  - 限流/队列：Redis（非正确性真值）

### 1.4 一次低风险退款的完整链路

1. 用户先换取 Bearer Token，再发“我要退款 + 订单号”；API 从认证 Principal 取 `user_id` 并校验订单归属，不信任请求体身份。
2. `accept_message` 创建/绑定 Ticket，写用户消息，创建 `queued` AgentSession，提交 DB。
3. API 在限流后投递 Celery；本地模式可改为后台线程，并立即返回 session id。
4. worker 读取最新用户消息、Ticket 状态/版本和历史，组装 AgentContext。
5. AgentCore 做结构化意图识别，路由 RefundHandlingSkill。
6. plan 只开放只读工具；harness 做白名单、参数绑定、工具审计和 token 记账。
7. finalize 以数据库事实核对资格和风险；低风险只写 `pending_action`，Ticket 进入 `waiting_user_confirm`，**此时不建退款单**。
8. 用户第二轮回复“确认”；runner 从 Ticket 恢复确认态，专用 parser 只认强确认/强取消。
9. finalize 校验 pending_action 的类型、订单和 TTL，调用退款 service 建草稿；三层幂等与 DB 唯一约束兜底。
10. runner 写 Agent 回复，并用 `status + version` 做 Ticket CAS；退款、回复、状态更新在同一外层事务提交。若 CAS 冲突，全部回滚并把 Session 标为 failed，交 Celery 重试。
11. 客户端通过 SSE/轮询看到 `completed`；工具、token、状态和耗时可从会话视图与审计表复盘。

高风险退款在第 7 步直接建 `pending_human` 草稿和人工工单；真正“打款”不在本系统。

### 1.5 为什么需要 Agent，而不是只有意图分类 + 状态机

- 传统分类器 + 状态机足以承担**执行层**，而且本项目刻意保留这部分确定性。
- Agent 的增量价值在：
  - 任意自然语言、多轮历史和多候选冲突的语义理解；
  - 只读域内根据问题自主选择核对哪些工具、以什么顺序补信息；
  - provider 可替换的解释与摘要能力。
- 边界必须诚实：当前业务 Skill 的最终回复大多由代码查库拼模板，开放式规划空间有限。项目主张的是“**理解/核对有自主性，执行有确定性**”，不是自主程度越高越好。

### 1.6 明确不做

- 不做真实支付打款、支付账户变更、售前购物和开放域助手。
- 不做多 Agent、MCP Server、向量长期记忆和复杂 RAG；当前政策检索是轻量关键词/分类检索。
- 不做企业级 IAM/OAuth、refresh token、密钥轮换和细粒度权限策略；当前实现的是项目内 HMAC Bearer Token + `user/admin` 两级 RBAC。
- 不做完整人工客服接管操作闭环、Alembic 迁移、生产监控告警。
- 不把并发正确性测试说成 QPS/P99，不把 Stub 评测说成真实模型泛化。

- **追问**：一个只查询订单的请求为什么也创建 Ticket？这对数据量、SLA 和会话模型有什么代价？
- **追问**：如果没有 Agent，只保留规则和状态机，哪些能力会下降？当前代码里能否具体指出 LLM 真正参与的位置？
- **翻代码**：`app/api/chat.py`、`app/services/chat_service.py`、`app/workers/runner.py`、`app/agent/agent_core.py`、`app/skills/refund_handling/handler.py`。
- **跑证据**：`.venv/bin/python -m scripts.demo_recruitment`、`.venv/bin/pytest tests/test_chat_api.py tests/test_skills.py -v`。
- **回填**：`面试问答.md` 的讲法与证据矩阵。

## 2. 五个技术深挖方向

### 方向一 · Agent 编排与安全内核 ★王牌

- **业务风险**：LLM 越权查单、绕过确认、直接调用写工具、输出违规承诺。
- **主链路**：`AgentCore.handle → plan → _run_loop → _exec_tool → Skill.finalize → _finish`。
- **深究**：
  - 读写分离为什么是脊椎；
  - 白名单、危险 precheck、IDOR 参数绑定、工具审计、token 记账如何织入 loop；
  - pending_action 二次确认与 finalize 确定性写；
  - 哪些闸真实生效，哪些只是预留：当前 precheck 只记日志，真正挡写工具的是白名单和 finalize 边界。
- **失败策略**：白名单外 fail closed；上下文二次超限转人工；危险业务缺上下文转人工；回复 postcheck 降级安全话术。
- **追问**：
  - LLM 不调只读工具直接回答怎么办？哪些 Skill 仍用查库模板保证事实？
  - precheck 为什么当前价值接近 0？将来做参数校验应放在绑定前还是后？
  - 换 LangGraph/LangChain 时哪些是 wrapper，哪些是 callback，finalize 是否保留？
- **证据**：`tests/test_agent_loop.py`、`tests/test_context_backstop.py`、`tests/test_skills.py`。

### 方向二 · 幂等、事务与并发正确性 ★硬证据

- **业务风险**：重试/重复点击/换措辞/真并发导致重复退款；stale worker 覆盖工单状态；CAS 冲突后提交半成品。
- **主链路**：消息唯一键 → 退款请求键/业务键 → DB 唯一约束 → runner 外层事务 → Ticket version CAS。
- **深究**：
  - 三层退款幂等各防什么，`request_hash` 与 `business_key` 的区别；
  - `get_active_refund` 为什么是跨轮独立维度；
  - PostgreSQL 唯一约束 + IntegrityError 回查如何关闭 TOCTOU；
  - service 为什么不能在 Agent 事务中提前 commit；
  - SQLite 与 PostgreSQL 的并发语义差异。
- **失败策略**：唯一冲突回查赢家；CAS 冲突整事务回滚后由 Celery 重试；真正支付幂等交给下游。
- **追问**：
  - 换退款原因能否绕过 business_key？为什么会话级幂等仍需要？
  - 64/16 线程证明的是正确性还是吞吐？
  - `POST` 消息幂等的“先查后插”遇到真并发时如何收口？答案：嵌套事务捕获唯一键 `IntegrityError`，失败方回查赢家 Session 并返回 `dedup=true`。
- **证据**：`tests/test_refund_idempotency.py`、`tests/test_concurrency.py`、`tests/test_message_idempotency_concurrency.py`、`tests/test_worker_robustness.py`。

### 方向三 · 意图理解与对话流转 ★智能层

- **业务风险**：“能退款吗”“我不想退款了”“不确定”被误判成执行，或补订单号后丢失原意图。
- **主链路**：规则候选召回 → 极性/多候选处理 → LLM defer → SkillRouter → 状态机 → pending_context 跨轮恢复。
- **深究**：
  - 关键词为什么只召回不触发；否定/疑问/肯定映射；
  - 多候选无 LLM 时为何安全澄清；
  - INFO_REQUIRED 如何保存 intent/skill/slots，允许新意图打断；
  - 硬事实查 DB、软历史滚动摘要；为什么不上向量记忆。
- **失败策略**：低置信澄清；确认不清保持等待；LLM 分类失败回退通用咨询；上下文超限最终转人工。
- **追问**：
  - 规则未命中时 Stub 和真实 LLM 的行为分别是什么？
  - 摘要摘丢退款原因会怎样？哪些字段应从“软记忆”升级为结构化槽位？
- **证据**：`tests/test_intent.py`、`tests/test_skills.py::test_refund_question_does_not_create_draft`、`tests/test_chat_api.py` 的补槽场景。

### 方向四 · 高并发与可用性 ★已有基线，容量仍需治理

- **业务风险**：流量灌爆队列和 LLM 成本；provider 故障连锁；worker 崩溃丢任务；长输入盲重试。
- **主链路**：API 限流 → Celery 入队 → worker 消费 → LLM 熔断/fallback/backstop → DB 状态。
- **深究**：固定窗口 `INCR+EXPIRE`/fail-open、熔断三态/单探针/generation、`acks_late + prefetch=1 + timeout + retry`。
- **失败策略**：Redis 限流故障 fail-open；provider 熔断快速失败/走 fallback；可缩短的超限仅压缩重试一次；危险流程无法安全继续则转人工。
- **证据边界**：
  - `scripts/e2e_real_infra.py` 已对真实 Redis 固定窗口、真实 broker 入队和 worker 消费做验收；CI 也会启动真实 worker/API 复现。
  - `acks_late`、重试和超时已有配置/单测，但 worker 被强杀后的 redelivery 尚未做自动化故障注入。
  - PostgreSQL 并发测试证明退款正确性，不证明吞吐。
  - 归档基线 `loadtest/results/20260727-192419/`：50 用户、30 秒、4396 请求、0 失败、151.5 RPS、P95 68ms、P99 110ms、队列峰值 3089；仅代表本机 Stub 接入/削峰。
- **追问**：固定窗口双倍突刺、Redis fail-open 被打穿、多进程各一 HALF_OPEN 探针、实际 worker 数和瓶颈。
- **证据**：`tests/test_ratelimit.py`、`tests/test_circuit_breaker.py`、`tests/test_worker_robustness.py`、`.github/workflows/core-verification.yml`。

### 方向五 · 可观测与质量工程

- **业务风险**：Agent 黑盒不可追责；改提示词后流程回归；Stub 漂亮分数被误当真实泛化。
- **主链路**：HTTP middleware 接收/生成 trace_id → Celery task 参数跨进程传递 → runner/contextvar → ToolRegistry 审计与日志 → Session token/cost 回写 → metrics/admin 查询；评测脚本另行运行。
- **深究**：
  - trace_id 作为任务参数传到 worker，并重新写入 contextvar；Celery 接管日志 handler 后仍需显式安装 TraceFilter，E2E 会在 worker 日志断言同一值；
  - 工具审计、token 成本哪些进入主链路；
  - 两层评测中 StubJudge 与真实 Judge 的区别；
  - `quality_reviews` 表为何仍是预留。
- **失败策略**：可观测组件尽量不阻断主流程；Judge/真实模型评测不进在线请求。
- **证据**：`tests/test_tracing.py`、`tests/test_pricing.py`、`tests/test_eval.py`、`tests/test_judge.py`。

## 3. 最终方向 · 面试证据与边界 ★必须收口

### 3.1 机制成熟度矩阵

| 机制 | 是否进主链路 | 当前可复现证据 | 必须保留的边界 |
|---|---|---|---|
| 认证/RBAC、资源归属 | 是 | 登录/API/越权单测 + 真实 E2E | 最小 HMAC Token；无企业 IAM、refresh/key rotation |
| 读写分离、确认门、参数绑定 | 是 | Agent/Skill/API 回归 + 5 分钟演示 | precheck 仍是占位 |
| 退款三层/会话级幂等 | 是 | SQLite 单测；CI/本机 PostgreSQL 16 线程 | 历史手工 64 线程不是吞吐；真正打款不在本系统 |
| 消息接入幂等 | 是 | SQLite + PostgreSQL 16 线程 barrier | 只保证同一 `client_message_id`；客户端必须稳定复用键 |
| Ticket version/CAS | 是 | 确定性交错测试；退款副作用回滚测试 | 尚无 PG 多 worker 专项压测 |
| Redis 固定窗口限流 | 是（生产配置） | FakeRedis/API 测试 + 真实 Redis E2E | 断连 fail-open 尚无自动化故障注入 |
| Celery 异步消费 | 是（`agent_dispatch=celery`） | 单测 + 真实 broker/worker E2E | worker 强杀 redelivery 尚无自动化故障注入 |
| 熔断/fallback/backstop | 是 | 线程并发与脚本化 client 单测 | 熔断状态仅进程内 |
| trace/tool audit/token cost | 是 | 单测 + E2E worker 日志/DB 行 | 不是 OpenTelemetry；没有跨外部 provider 的 trace span |
| 两层评测 | 离线链路 | 47 回合 Stub 可复现；历史真实 Qwen 记录 | 样本小；真实模型结果不是每次 CI 复现 |
| SSE | 是 | 服务生成器/API 测试 | 是任务进度流，不是 token 流 |
| 自动质检写 `quality_reviews` | 否 | 只有表和离线 Judge | 不能说“会话结束自动质检已落地” |
| Locust 接入/削峰基线 | 离线运行链路 | 归档 CSV/summary：151.5 RPS、P95 68ms、P99 110ms | 单机 Stub，不是 LLM/生产容量 |
| 人工客服操作闭环 | 否 | 只读管理端与摘要 | 尚无接单/回复/解决/关闭 |
| MCP/向量 RAG/多 Agent | 否 | 仅设计边界或未实现 | 不列为项目能力 |

### 3.2 三个必须会讲的 Bad Case

1. **越权 Bad Case**
   LLM 被诱导把 `user_id/order_id` 填成他人的值。harness 在执行前用 AgentContext 真值覆盖参数，测试断言最终查的是本人订单；API 对显式传入的他人订单/工单直接拒绝。
   证据：`test_context_binding_overrides_llm_args`、`test_accept_message_rejects_other_users_order`。
   现在 API 身份来自 Bearer Token；即使请求体伪造别人的 `user_id` 也会 403，普通用户访问 admin 也会 403。
   证据补充：`tests/test_auth.py`。边界：当前是项目内 Token，不是企业身份系统。

2. **并发幂等 Bad Case**
   多线程同抢一笔退款时，前置查询都可能看不到记录；最终由 PostgreSQL 唯一约束裁决，失败事务回查赢家，所有请求拿到同一 id。另一个并发风险是 stale worker：Ticket CAS 失败时退款/回复/附加工单必须一起回滚。
   消息接入同样用 PostgreSQL 唯一约束裁决，失败方在 savepoint 中捕获 `IntegrityError` 并回查赢家，不返回 500。
   证据：`test_concurrent_same_refund_creates_one_row`、`test_concurrent_same_client_message_returns_one_session`、`test_runner_cas_conflict_rolls_back_refund_write`。
   边界：只能去重稳定复用同一 `client_message_id` 的重放。

3. **意图误判 Bad Case**
   “能退款吗”过去若按关键词会被当申请；“不确定”包含“确定”也可能误执行。现在关键词只召回，疑问映射为只读咨询，确认态使用专用 parser，迟疑保持等待且不建草稿。
   证据：`test_refund_question_does_not_create_draft`、`test_uncertain_in_confirm_does_not_execute`。
   边界：真实长尾表达仍依赖 LLM，当前 47 回合不足以证明线上泛化。

### 3.3 结束前的证据核对动作


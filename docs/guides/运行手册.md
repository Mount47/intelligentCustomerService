# SupportFlow 运行手册（新人上手版）

> 本文负责“怎么运行”。当前能力与动态数字以
> [项目状态](../architecture/项目状态.md) 为准。

面向第一次拿到本项目的人：怎么启动、怎么配置、怎么在前端提问、怎么看到结果与**整个处理过程**、遇到问题或回答不准怎么改。

> 一句话：SupportFlow = 电商售后智能客服工单 Agent。链路 = 意图识别 → 查订单/物流 → 按规则判断 → 调工具 → 工单状态流转 → 自动解决或转人工 → 记录 → 评测。
> 当前设计细节见 [架构文档](../architecture/01-项目总览.md)。

---

## 0. 前置要求
- **Python 3.11+**（必须；项目用了 3.10+ 语法）
- **Node.js 18+**（前端，可选）
- 可选：**Docker**（跑全栈/真实队列/压测时才需要）
- 可选：一个 LLM API key（**千问百炼 / DeepSeek / OpenAI 兼容**最方便；不填则用内置 `stub` 假模型，业务流程照样跑）

> 说明两种运行档位：
> - **本地轻量**（推荐新人）：无需 Docker/Redis/Celery，sqlite + 后台线程即可跑通全链路。
> - **Docker 全栈**：PostgreSQL + Redis + Celery + API，演示真实队列削峰 / 压测时用。

## 1. 最快五分钟体验（零依赖，连服务器都不用）

```bash
# 在项目根目录
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -e .                                        # 安装全部依赖
DATABASE_URL=sqlite:///./local.db LLM_PROVIDER=stub python -m scripts.demo_local
```
会直接打印 4 个场景的**回复 + 思考步骤 + token**。这一步验证「业务链路通了」，用 `stub` 假模型，零 token 零成本。

想用真实模型（千问示例）：
```bash
DATABASE_URL=sqlite:///./local.db \
LLM_PROVIDER=qwen LLM_MODEL=qwen-plus \
OPENAI_API_KEY=sk-你的百炼key OPENAI_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1 \
python -m scripts.demo_local
```

## 2. 完整本地启动（后端 HTTP + 前端，推荐）

### 2.1 配置 `.env`
```bash
cp .env.example .env
```
编辑 `.env`，本地最小配置：
```ini
DATABASE_URL=sqlite:///./local.db
AGENT_DISPATCH=thread          # 本地用后台线程跑，无需 Redis/Celery
LLM_PROVIDER=stub              # 或 qwen / deepseek / claude（见 §4）
# 若用真实模型，按 §4 填 key 与 base_url
```

### 2.2 造数据（含场景对照表）
```bash
python -m scripts.seed_data
```
结束会打印一张**场景对照表**：每个 `order_id / order_no / 建议消息 / 预期场景`，覆盖退款各风险、物流各情况等。照着发消息即可逐个验证。

#### 可选：批量数据（真实对话测试用）
想在"接近真实分布"的数据上跑大量对话、看运维端指标好看，再补一条：
```bash
python -m scripts.seed_bulk        # 在 seed_data 之后跑
```
生成 **50 用户 / 500 订单（含明细）/ 物流（含约 10% 异常件）/ 200 历史工单+消息 / 150 Agent 会话+工具调用 / 40 笔历史退款**，分布接近真实（45% 已签收、25% 在途…）。
- **纯本地造数，零 token、零 LLM 调用**（数据从代码内预定义池里 random 组合）。
- **幂等**：检测到 `bulk_user001` 已存在则跳过，可安全重跑。
- 两脚本分工：`seed_data` 造**可复现场景订单**（评测/边界用），`seed_bulk` 造**量**（真实对话/看板用）。结束打印前 10 个可测用户的 `user_id`。

### 2.3 起后端
```bash
uvicorn app.main:app --reload          # http://localhost:8000
```
- 健康检查：`curl localhost:8000/health`
- 接口文档（Swagger）：浏览器开 `http://localhost:8000/docs`

### 2.4 起前端
```bash
cd frontend
npm install
npm run dev                             # http://localhost:5173
```
> `frontend/.env.local` **已预置**（连真实后端，非 mock）：
> ```ini
> VITE_API_BASE_URL=/api                 # Vite 原样代理到后端 /api
> VITE_USE_MOCK=false                    # dev 也连真后端
> VITE_ENABLE_MOCK_FALLBACK=false        # 后端失败必须显式报错
> ```
> 机制（`src/api/client.ts`）：`VITE_USE_MOCK=true` 强制 mock；`=false` 强制连真后端（即便 dev）；
> **都不设**时 dev 默认走内置 mock 假数据（方便无后端预览 UI）。
> 真实请求失败会直接显示错误；只有显式设置 `VITE_ENABLE_MOCK_FALLBACK=true` 才允许回退 mock，避免联调/生产展示假成功。
> 历史坑：旧逻辑 `|| import.meta.env.DEV` 会让 dev 永远走 mock（设 false 也无效），已修为"显式设置优先"。

## 3. 怎么提问 / 看结果 / 看整个过程

### 3.1 用户售后端（`http://localhost:5173`）
1. 可用以下任一账号登录：
   - `demo / supportflow-user`：技术边界场景。
   - `demo_vip / supportflow-user`：更贴近真实用户，包含14笔固定订单，覆盖待付款、待发货、
     正常运输、派送、物流停滞、物流异常、签收未收到、普通退款、高额退款、生鲜、
     定制商品、超期售后和已取消订单。
2. 页面只展示当前账号自己的订单；找到目标订单，点「申请售后」。
3. 进入对话后直接说明问题，如「我想申请退款」。订单已由页面自动关联，不需要手动输入订单号。
4. 右侧显示用户能理解的处理进度；服务端事件流连接异常时，自动改用轮询更新结果。
5. 不涉及具体订单的问题，可在订单页点「咨询其他问题」。

低风险退款或退货会在对话中显示明确的确认卡片。第一次点击只展示订单、商品和金额，
第二次点击「确认提交」才会通过 `POST /api/chat/action` 创建申请；「取消申请」一次点击即可。
需要审核或人工处理时，订单和对话记录会一起转交。

#### 用接口直接提问（带订单编号，能跑通所有分支）
```bash
# 先登录获取访问凭证（账号密码以 seed 输出为准）
TOKEN=$(curl -s localhost:8000/api/auth/token -H 'content-type: application/json' \
  -d '{"username":"demo","password":"supportflow-user"}' | \
  python -c 'import json,sys; print(json.load(sys.stdin)["accessToken"])')

# 发消息（orderId 用 seed 对照表里的值，用户身份来自访问凭证）
curl -s localhost:8000/api/chat/message \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"content": "我要退款", "orderId": 54}'
# 返回 {"sessionId": N, "taskStatus": "queued", ...}

# 轮询拿结果 + 思考过程 + 工具调用
curl -s localhost:8000/api/chat/session/N \
  -H "authorization: Bearer $TOKEN" | python -m json.tool
```
返回里能看到：`latestReply`（回复）、`steps`（思考时间线）、`toolCalls`（工具调用审计，含 input/output）、`tokenUsage`。

或用无服务器脚本 `python -m scripts.demo_local` 一次跑通预设场景。

### 3.2 管理员端 = 运维监测端（`http://localhost:5173/admin`）
看「整个过程」与运行指标：
- **指标看板**：工单量 / 解决率 / 转人工率 / 平均 token 成本 / P95 延迟 / 活跃会话
- **工单列表 + 详情**：状态机时间线
- **会话列表 + 详情**：每次会话的意图/技能/状态 + **工具调用审计**（每个工具的输入/输出 JSON、成功与否、耗时）
- 对应后端接口：`GET /api/admin/metrics`、`/api/admin/tickets(/{id})`、`/api/admin/sessions(/{id})`

### 3.3 后端日志（全链路追踪）
后端每条日志都带 `[trace_id]`，一次会话的意图识别、状态转移、工具调用、token 记账都用**同一个 trace_id**串起来：
```bash
# 起后端的终端里直接看；或重定向到文件后按 trace_id 过滤
uvicorn app.main:app --reload 2>&1 | grep <trace_id>
```

## 4. 配置说明（`.env`）

| 变量 | 作用 | 示例/默认 |
|---|---|---|
| `DATABASE_URL` | 数据库 | 本地 `sqlite:///./local.db`；docker `postgresql+psycopg://supportflow:supportflow@db:5432/supportflow` |
| `AGENT_DISPATCH` | 任务调度 | `thread`（本地无中间件）/ `celery`（docker 真队列） |
| `LLM_PROVIDER` | 模型厂商 | `stub`/`claude`/`deepseek`/`qwen`/`gpt`/`vllm`/`ollama` |
| `LLM_MODEL` | 模型名 | 见下表 |
| `ANTHROPIC_API_KEY` | Claude key | （provider=claude 时） |
| `OPENAI_API_KEY` / `OPENAI_BASE_URL` | OpenAI 兼容族 key/地址 | （deepseek/qwen/gpt/vllm 时） |
| `LLM_MAX_TOKENS` / `LLM_THINKING` | 输出上限 / 思考 | `16000` / `adaptive` |
| `REFUND_HIGH_AMOUNT_THRESHOLD` | 高金额退款阈值（>则人工） | `500` |
| `REFUND_RETURN_WINDOW_DAYS` | 售后期天数（签收超过则人工） | `7` |
| `LOGISTICS_STALE_HOURS` | 物流无更新阈值（催件） | `48` |
| `CORS_ORIGINS` | 允许的前端来源 | `*`（本地） |
| `STUB_DELAY_MS` | 压测时给 stub 加模拟时延 | `0` |

### 切换模型（改 `.env`，不动代码）
| 厂商 | LLM_PROVIDER | LLM_MODEL | 其他 |
|---|---|---|---|
| 内置假模型 | `stub` | 任意 | 无需 key（业务流程照跑） |
| Claude | `claude` | `claude-opus-4-8` | `ANTHROPIC_API_KEY` |
| 千问百炼 | `qwen` | `qwen-plus` | `OPENAI_API_KEY` + `OPENAI_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1` |
| DeepSeek | `deepseek` | `deepseek-chat` | `OPENAI_API_KEY` + `OPENAI_BASE_URL=https://api.deepseek.com/v1` |
| 本地 vLLM | `vllm` | 你的模型名 | `OPENAI_BASE_URL=http://localhost:8000/v1` |

## 7. 常见问题排查

| 现象 | 原因 / 解决 |
|---|---|
| `ModuleNotFoundError: No module named 'app'` | 用 `python -m scripts.xxx` 在**项目根目录**跑，别 `python scripts/xxx.py` |
| 前端显示的是演示数据 | `VITE_USE_MOCK=true`；真实联调改为 `false`，并保持 `VITE_ENABLE_MOCK_FALLBACK=false` |
| 前端直接提示 HTTP/网络错误 | 真实模式不会静默回退 mock；检查后端 8000 端口、`/health` 与 Vite 代理 |
| 模型报 `401 / model not found` | key 没填或百炼/DeepSeek 控制台未开通该模型；换 `qwen-plus` 等 |
| 模型报 `tools` 400 | 个别模型不支持 function calling，换 `qwen-plus`/`qwen-max`/`deepseek-chat` |
| 退款/物流回复「请补充订单号」 | 消息中未提供可识别订单号，属正常索取信息分支；下一轮发送订单号即可续接 |
| 端口被占用 | 后端 `--port 8001`，前端 vite 会自动换端口 |
| sqlite 报锁 | 本地高并发用 docker + PostgreSQL；日常单人用 sqlite 足够 |

## 8. 回答不准 / 不对，去哪里改 ★

按"症状 → 改哪里 → 怎么验证"定位。**改完都用 `python -m app.eval.run_eval` 跑一遍评测**确认没改坏。

| 症状 | 改哪里 | 说明 |
|---|---|---|
| **意图识别错**（如「催一下」没认成物流） | `app/agent/intent_classifier.py` 的 `_KEYWORDS` 关键词表 | 加/调关键词；模棱两可的交给 LLM 兜底（已内置） |
| **路由到错的技能** | 各 Skill 的 `triggers`（`app/skills/*/handler.py`）+ `app/agent/skill_router.py` | 意图→技能映射 |
| **退款风险判断不对**（该人工的自动了/反之） | `.env` 的 `REFUND_HIGH_AMOUNT_THRESHOLD` / `REFUND_RETURN_WINDOW_DAYS`；逻辑在 `app/services/refund_service.py::evaluate_refund_risk` | 阈值改 .env 即可；规则改 service |
| **物流催件阈值不对** | `.env` 的 `LOGISTICS_STALE_HOURS` | 默认 48h |
| **回复乱承诺**（保证退款/赔偿） | `app/agent/guardrails.py` 的 `FORBIDDEN_PHRASES`（禁语）；命中会降级为安全话术 | 加禁语；对抗样例在评测里量化拦截率 |
| **回复话术 / 模板不好** | 对应 Skill 的 `finalize`（`app/skills/refund_handling/handler.py` 等）的回复文案；通用兜底在 `app/skills/general.py` | 退款/物流的最终话术是确定性模板 |
| **政策内容过时 / 检索不到** | 政策文本：`scripts/seed_data.py` 的 `POLICIES`；检索关键词：`app/services/knowledge_service.py` 的 `CATEGORY_KEYWORDS` | 改完重新 seed |
| **模型本身答得差** | `.env` 换更强模型（`LLM_PROVIDER`/`LLM_MODEL`，见 §4）；或调 Skill 的系统提示 `_SYSTEM` / `instructions.md` | 换 qwen-max / claude 等 |
| **危险动作被 LLM 触发** | 设计上写操作（建退款/转人工）由 `finalize` 确定性执行，LLM 只读；如需调，改对应 Skill 的 `plan.allowed_tools` 白名单 | 不可逆动作不交给 LLM |

> 原则：**业务判断（退款是否人工、物流是否异常）是确定性代码 + 配置阈值，不依赖模型**；模型负责理解与措辞。所以"判断不对"多半改 `.env` 阈值或 service 规则，"话术/理解不对"才改提示词或换模型。

## 9. 目录速查
```
app/
├── api/         接口：health / chat / admin
├── agent/       Agent 核心：意图/路由/状态机/guardrails/harness(agent_core)
├── skills/      业务技能：refund_handling / logistics_exception / general
├── services/    业务逻辑：order/logistics/refund(三层幂等)/ticket/sla/knowledge/chat/admin
├── tools/       业务工具 + 注册表（统一结果，自动审计）
├── llm/         LLM 抽象 + Claude/OpenAI兼容 适配器 + registry
├── workers/     runner(纯处理) + celery 任务
├── observability/ metrics（指标）+ tracing（trace_id）
├── eval/        评测集 test_cases.json + run_eval
└── db/          数据模型 + 数据库会话 + 初始化
scripts/         seed_data（含场景对照表）/ demo_local（无服务器体验）
loadtest/        locustfile（接入层压测）
frontend/        Vue3 + Element Plus（用户聊天端 / 运维监测端）
deploy/          Dockerfile + docker-compose
docs/            当前架构 + 学习指南 + 面试资料 + 历史归档
```

# SupportFlow 分模块学习路线

这份路线用于真正理解项目，不以背文件和背术语为目标。每个模块都要回答四个问题：

1. 它解决什么业务问题？
2. 没有它会出现什么具体错误？
3. 它在完整请求链路的哪个位置？
4. 哪些测试或运行结果能证明它？

动态规模与测试结果统一查看 [项目状态](../architecture/项目状态.md)。

## 第一阶段：建立业务和数据基础

### 模块一：业务范围

- [ ] 阅读 [项目总览](../architecture/01-项目总览.md)
- [ ] 说清系统支持和不支持的业务
- [ ] 解释为什么既有大模型，也保留大量确定性代码
- [ ] 区分退款申请与真实资金退款

自测：

> 为什么这个系统不是普通聊天机器人？如果去掉大模型，哪些能力仍然可以运行？

### 模块二：数据模型

- [ ] 阅读 [业务与数据模型](../architecture/02-业务与数据模型.md)
- [ ] 对照 `app/db/models.py`

建议测试：

```bash

```

## 学习结束后的总检查

不看文档，完整讲清：

1. 一条用户消息的生命周期；
2. 一次低风险退款的两轮流程；
3. 一次高风险退款为什么转人工；
4. 重复消息、重复任务和重复退款分别怎么防；
5. 模型越权、编造和服务故障分别怎么处理；
6. 当前项目有哪些明确未完成或未声称的能力。

如果只能说模块名称，不能说具体故障和证据，就还没有真正理解。
